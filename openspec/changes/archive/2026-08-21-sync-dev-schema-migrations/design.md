## Context

The migration engine lives in `libraries/framework/` (vendored, scoped `Kirki\Ecommerce\Framework\` namespace — see `CLAUDE.md`, don't use it as a style reference, but it is the real implementation):

- `config/migrations.php` is a plain PHP array of migration FQCNs. **Array order is run order** — there is no timestamp-prefixed filename convention.
- `CoreServiceProvider::register_migrations()` tags that array as `'app.migrations'`; `Migrator::run()` iterates it in order.
- Applied migrations are tracked in the WP option `framework_migrations` (key: FQCN, value: `{batch, ran_at}`) — **not** a `migrations` DB table. A migration already present as a key is skipped.
- `Schema::table('table', function (Structure $table) {...})` opens `MODE_ALTER`. In that mode `Structure` exposes `rename_column($from, $to)`, `drop_column($cols)`, `drop_index($keys)`, `drop_primary()`, `drop_foreign($cols)`, and `->change()` chained on a redeclared column builder for `MODIFY COLUMN`. `primary()`/`index()`/`foreign()` double as `ADD ...` in alter mode.
- All 40 existing migrations are `Create*Table` migrations using `Schema::create()`. **No alter migration exists anywhere in this codebase's git history** — these are the first. There's a scaffold stub (`libraries/framework/Console/stubs/migration-table.stub`) but its `use Framework\...` imports are unscoped/stale; real migration files use the scoped `Kirki\Ecommerce\Framework\...` imports (matching every existing `Create*Table.php`).
- The five `Create*Table.php` files were edited directly on `dev` to describe the new schema. That's correct for fresh installs (a new site runs the edited `Create*Table` as-is) but invisible to any site that already ran the original version of that migration — its FQCN is already a recorded key, so it never re-runs, and the site's live schema silently diverges from what the file now describes.

See proposal.md - Why, and the per-table breakdown in What Changes.

## Goals / Non-Goals

**Goals:**
- One alter migration per affected table, each registered in `config/migrations.php` immediately after that table's `Create*Table` entry.
- Each migration transforms only what changed for its table (per the proposal's per-table breakdown) — no unrelated cleanup.
- Establish a workable first-precedent pattern for alter migrations in this codebase, since none exists to imitate.
- Convert every native `enum` column in the codebase (14 columns across 5 tables) to `string` with allowed values documented via `->comment()`, so a future new allowed value is an application-level change, not a migration.

**Non-Goals:**
- No data remapping/backfill for carts or coupons (explicit product decision — alpha plugin, low data volume, carts are disposable, coupon eligibility columns didn't carry meaningful behavior in the prior release).
- No `down()` rollback behavior beyond satisfying the `Migration` interface (mirrors existing `Create*Table` migrations, which also don't implement meaningful rollback logic beyond dropping what they created).
- No audit of application code (DTOs, requests, resources) that reads or writes these columns — request-level validation (e.g. `CouponCreateRequest`, `CouponUpdateRequest`) already constrains allowed values in PHP independent of the DB column type, so this is treated as safe to leave unaudited; see Risks.

## Decisions

**Revert the five edited `Create*Table.php` files to their `main`-branch (originally-released) content; the new alter migrations carry the full delta.** This isn't just convention — it's required for correctness given how `Migrator::run()` actually works: on any install where a migration's FQCN isn't yet recorded (including a brand-new install, where nothing is recorded until the first run), it runs *every* registered migration in `config/migrations.php` order, sequentially. If `Create*Table.php` already described the final (`dev`) shape while the newly-appended alter migration still tried to `drop_column('customer_id', ...)` or `drop_column('customer_eligibility', ...)`, a fresh install would run both back-to-back and the alter migration would fail — those columns wouldn't exist under their old names, because `Create*Table` already produced the new shape directly. Reverting `Create*Table.php` to the original (`main`) shape makes the sequential replay correct for every install: fresh installs run `Create*Table` (original) → alter migration (delta) → final shape, exactly the same path an upgrading site takes. `main` is the actually-released baseline real sites are running, so reverting to it (rather than treating `dev`'s edits as truth) also matches the general convention this proposal is otherwise following: never edit an already-shipped migration, always add a new one. Alternative considered: leave `Create*Table.php` edited and make the alter migrations defensively check column/key existence before acting (e.g. only rename if the old column exists) — rejected as needless conditional complexity when reverting the file removes the problem outright.

**One migration class per table, not one combined migration.** Matches the existing convention of one table per migration file, keeps each change independently reviewable, and means a failure in one table's alter doesn't block the others (each is a separate `ALTER TABLE` transaction/statement via `Compiler::compile_alter()`).

**Every column change in this proposal is `drop_column` + add, never `rename_column` — including `carts.customer_id` → `user_id`.** `rename_column` compiles to a plain SQL `CHANGE COLUMN`, which relabels a column but carries its existing values forward byte-for-byte. That's only safe when the old and new column hold the same *kind* of value. `carts.customer_id` and `user_id` don't: the old column held `kirki_ecommerce_customers.id` values, the new column holds `users.ID` values — a completely different ID space. Renaming would silently carry forward integers that are wrong under their new meaning, and would very likely make `up()` itself fail on any site with non-null `customer_id` data, since those stale values won't satisfy the new `user_id → users.ID` foreign key being added in the same migration. Dropping the old column and adding the new one guarantees no stale value can ever land in `user_id` — it starts genuinely empty, matching the decision below that pre-upgrade cart-owner associations are discarded, not remapped. `coupons.customer_eligibility`/`exclude_customers` → `customer_include_eligibility`/`customer_exclude_eligibility` follows the same drop+add shape, for the same reason (different value vocabulary, not a relabeling). The enum-to-string conversions are the one place this proposal legitimately preserves a column's identity via `->change()` (`MODIFY COLUMN`, not `CHANGE COLUMN` with a rename) — those columns keep their name and their existing values keep the same meaning, only the storage type widens.

**Every `enum` column becomes `string(50)` with a `->comment()` listing the allowed values, default and nullability preserved.** Rationale: a database `enum` bakes its allowed value set into the column definition, so adding one more value later requires exactly the kind of alter migration this proposal exists to introduce — the project has decided that's not worth repeating for every future value addition. `string(50)` comfortably fits every current value (longest is `specific-customers` at 19 chars) with headroom; the comment (e.g. `'Supported values: code, automatic'`) keeps the allowed set discoverable without a schema enum, matching the existing convention of using `->comment()` for column-level documentation (e.g. `cart_token`'s "For guest cart tracking"). Applies to two kinds of columns: the 3 new coupon columns this proposal is already adding (declared as `string` from the start — no conversion needed, they don't exist in any live database yet) and 11 pre-existing `enum` columns across `kirki_ecommerce_coupons` (6), `kirki_ecommerce_addresses` (1), `kirki_ecommerce_attributes` (1), `kirki_ecommerce_scheduler_jobs` (1), and `kirki_ecommerce_refunds` (2), each converted in place via a column redeclared with `->change()`. The latter group is unrelated to the dev/main diff — these tables are otherwise untouched by this proposal — but reuses the same alter-migration mechanism, so it's bundled into this change rather than opened as a separate one. Kept as a **separate migration per table from the dev/main-diff migration** (e.g. `AlterCouponsEnumColumnsToString` alongside `AlterCouponsEligibilityColumns` for `coupons`) so the two concerns — syncing the dev/main schema diff vs. the enum-to-string policy change — stay independently traceable and revertible.

**FK and index changes travel with their column.** For `carts`, dropping the old FK/index/column and adding the new ones happens in one migration, in this order: `drop_foreign` → `drop_index` → `drop_column('customer_id')` → add `user_id` column → `index(...)` → `foreign(...)`. Dropping the old FK and index before the column they reference avoids trying to drop a column a constraint still points at.

**No pre-migration data transform for carts or coupons.** Per explicit product direction: carts are ephemeral/expiring (already have `expires_at` + cleanup indexes, so treating pre-upgrade rows as disposable is consistent with existing design intent), and the coupon eligibility columns "didn't matter" in the prior release. Alternative considered: `UPDATE` old values forward before dropping columns — rejected as unnecessary complexity for data the product owner has said not to preserve.

**No default-row backfill for `shipping_profiles.is_default` / `tax_profiles.is_default`.** Adding the column with `default(0)` is sufficient; whether an existing multi-profile site needs exactly one row flipped to `1` is a UI/product concern (e.g. "pick your default" prompt), not a schema-migration concern — out of scope here per explicit product direction.

**Registration order:** append each new alter migration directly after its table's `Create*Table` entry in `config/migrations.php`, preserving the existing entries' relative order for everything else. This satisfies the FK dependency the `carts` migration has (the `users` table already exists as a WP core table, no ordering issue there).

## Risks / Trade-offs

- **[Risk] This is the first alter migration in the codebase — the `Structure`/`Compiler` alter path is exercised for the first time by app code.** → Mitigation: keep each migration mechanically small and directly traceable to a diff hunk in the proposal; rely on the framework's own alter-mode guards (`guard_altering()` throws outside `MODE_ALTER`) to catch misuse early. No automated test harness for migrations was found in this codebase — verification will be manual (see tasks.md).
- **[Risk / accepted trade-off] Existing cart owner-associations and coupon eligibility configuration are dropped, not migrated.** → Mitigation: none — explicitly accepted per product direction, documented in the proposal as **BREAKING**.
- **[Risk] Converting `enum` to `string` removes MySQL's own value-validity enforcement at the database layer — a `string` column will silently accept a value outside the documented set, where an `enum` column would reject it.** → Mitigation: every affected column already has request-level PHP validation upstream of persistence (e.g. `CouponCreateRequest`, `CouponUpdateRequest`) — the DB-level constraint was redundant with an already-enforced application-level one, not the sole guard. No new validation is added here; existing validation is presumed sufficient and out of scope to re-verify column-by-column.
- **[Risk] `->change()` on a redeclared column reconstructs the full `MODIFY COLUMN` clause from what this migration declares (type, length, default, nullable, comment), not from the live column's current attributes.** If a live column's nullability or default drifted from what its `Create*Table.php` declares (e.g. via manual DB intervention), the conversion could silently discard that drift. → Mitigation: not otherwise mitigated — each conversion migration explicitly restates the same default/nullable the column's `Create*Table.php` already declares, so on an unmodified installation nothing changes; treated as acceptable given the earlier product framing that this plugin is alpha with little live data.
- **[Risk, discovered during verification] Alter migrations are not safely re-runnable if `record_migration()`'s tracking write is lost while the schema change it tracks survives.** `Migrator::run()` records a migration as applied via a separate `update_option()` call immediately after each migration's `up()` — there is no transactional link between the two. Under WordPress's own `WP_UnitTestCase` test harness this is directly observable: `start_transaction()` (called from `setUp()`, not `setUpBeforeClass()`) sets `autocommit = 0`, but any `ALTER TABLE` inside a later `setUpBeforeClass()`-triggered migration run causes MySQL's implicit commit — which also silently opens a *new* transaction that a subsequent test's rollback then discards, wiping the tracking write while the schema change itself (already committed by the implicit commit) persists. The next migrator run then sees the migration as "not yet applied" and re-attempts an `up()` that assumes pre-migration column names/constraints that no longer exist, failing outright. This is a **pre-existing structural gap in the migration engine**, invisible until now because every one of the 40 prior migrations was `CREATE TABLE IF NOT EXISTS` — inherently safe to re-run even if tracking was lost. This proposal's alter migrations are the first that are not idempotent, so the gap is exposed for the first time. → Mitigation: none applied here — fixing the engine's tracking/DDL atomicity is a `libraries/framework/` change, out of scope for this proposal (see `CLAUDE.md`: don't hand-edit the vendored framework). Worth a dedicated follow-up if more alter migrations are anticipated; a real (non-test-harness) site running `wp kirki migrate` outside of any wrapping transaction is not subject to this specific test-transaction/DDL interaction, but the underlying non-atomicity between the DDL and the tracking write is a latent risk on any site regardless (e.g., a crash between the two steps).
- **[Finding, pre-existing application bug, not caused by this proposal — resolved independently] `ShippingProfileService::create()` / `CreateShippingProfileDTO` (and the symmetric `TaxProfile` pair) didn't coalesce a missing `is_default` to `false` before insert.** Found via the integration suite: `POST /shipping-profiles` and `POST /tax-profiles` 500'd with "Column 'is_default' cannot be null" whenever the request omitted the field, because the DTO's untyped-default public property passed through as `null` and the framework's Model insert layer sent that `NULL` explicitly rather than omitting the column (which would let MySQL's own `DEFAULT 0` apply). This was identical regardless of whether `dev`'s own originally-edited `Create*Table.php` or this proposal's alter migration created the column — both produce the same `NOT NULL DEFAULT 0` shape — so it was not a consequence of any decision made in this proposal, and out of this proposal's "no API/application changes" scope to fix. Resolved independently (DTOs now default `is_default = false`, request validation rules changed to `nullable|boolean`); re-verified passing.

## Migration Plan

1. Revert the five `Create*Table.php` files (dev/main-diff tables) to their `main`-branch content exactly (`git show main:database/migrations/<file>.php`).
2. Add the five dev/main-diff alter migration classes to `database/migrations/`.
3. Add the five enum-to-string alter migration classes (`coupons`, `addresses`, `attributes`, `scheduler_jobs`, `refunds`) to `database/migrations/`. These don't depend on step 1/2 (different tables, or — for `coupons` — a different migration file) but are grouped here since they share the same alter-mode mechanism.
4. Append each new migration to `config/migrations.php` directly after its table's `Create*Table` entry (for `coupons`, both `AlterCouponsEligibilityColumns` and `AlterCouponsEnumColumnsToString` go after `CreateCouponsTable::class`, in either order relative to each other since they touch disjoint columns).
5. Manually verify two scenarios converge on the same schema: (a) a database seeded to look like a pre-`dev` install (`main`'s original `Create*Table` migrations already applied) running only the new alter migrations, and (b) a completely fresh install running the full migrator from scratch (`Create*Table` then its alter migration(s), for each table). Both must produce an identical final schema for all nine affected tables (column names/types, indexes, keys, FKs) matching what `dev`'s edited files described before being reverted, plus the enum-to-string conversion for the four tables outside the original diff.
6. No rollback path is provided beyond each migration's `down()` reversing its own `up()` — consistent with how existing `Create*Table` migrations handle `down()`.
