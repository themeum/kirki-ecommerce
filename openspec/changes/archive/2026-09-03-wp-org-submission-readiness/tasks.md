## 2. Exception-argument escaping findings (WordPress.Security.EscapeOutput.ExceptionNotEscaped, 373 findings)

**Correction during implementation**: the original plan here was to wrap
the translated message argument in `esc_html__()`. That was tried,
found to double-escape / corrupt output through the framework's actual
exception-handling paths (`ApiExceptionHandler` puts the raw message
into a JSON response; `SiteExceptionHandler` already calls `esc_html()`
itself before `wp_die()`), and reverted. See design.md's Decisions
section ("Correction during implementation"). All 373 findings in this
category — both the message argument and the ~171 non-message
arguments like `Response::NOT_FOUND` — are false positives for this
codebase's architecture (every `throw` here is caught centrally in
`libraries/framework/Route.php`, one call-stack frame above where the
sniff's own try/catch detection looks). The fix is a scoped
`// phpcs:ignore WordPress.Security.EscapeOutput.ExceptionNotEscaped -- <reason>`
on each flagged line, not a code change.
