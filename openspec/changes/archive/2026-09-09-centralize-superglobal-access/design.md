## Context

`Kirki\Ecommerce\Framework\Http\Superglobals` (`libraries/framework/Http/Superglobals.php`) already exists, vendored via `composer scope` from the sibling `themeum/framework` repo, and is confirmed in sync with its upstream source (diff shows only expected namespace-scoping differences). It exposes `server()`, `post()`, `query()`, `cookie()`, `files()` — each dual-mode: a `null` key returns the whole array unslashed-only, a string key returns one value both unslashed and run through `Sanitizer::apply_rule($value, $type)` (default `Sanitizer::TEXT`). Single-key reads reject non-scalar values by design (`is_scalar()` guard runs before the `Sanitizer` dispatch, regardless of `$type` — passing `Sanitizer::ARRAY` does not bypass it), returning the caller's `$default` instead. See proposal.md - Why for how this file came to exist and why this project should adopt it now.

This file is out of reach for hand-editing: it is regenerated by `composer scope`, which pulls from `/Users/ashraful/Projects/framework` (a separate git repo). This change only consumes the class as-is; it does not modify it.

The framework also provides `Kirki\Ecommerce\Framework\Http\Request`, built on top of `Superglobals` (`Route::dispatch_site()` and the REST dispatch path both call `Superglobals::query()/post()/files()/server()/cookie()` to build one, then bind it into the container as `app()->instance('request', $request)`). A global `request()` helper (`Framework\helpers.php`) resolves that singleton, with typed accessors (`->int()`, `->text()`, `->array()`, `->cookie()`, ...) reading from `$this->attributes = array_merge($query, $body, $route_params)`. This project already uses it in two places (`app/Services/CartService.php`, `resources/views/site/login.php`), confirming it's the established idiom for request-scoped reads, not a framework capability this project has been avoiding.

## Goals / Non-Goals

**Goals:**
- Every direct `$_GET`/`$_POST`/`$_SERVER`/`$_COOKIE` read in `app/`, `database/`, and `resources/views/site/*.php` goes through either `Superglobals` or `Request`/`request()`, whichever is the correct tool for that call site (Decision 0).
- Each conversion preserves existing behavior exactly, except the one accepted widening called out below.
- Document the convention in `CLAUDE.md` so future code defaults to one of these two, not a raw superglobal.

**Non-Goals:**
- No change to `Superglobals`, `Request`, `Sanitizer`, or any other vendored framework file.
- No change to `payments/kirki-*` packages (separate addon plugins) or `tests/` (superglobal writes for test fixtures, not reads either class could replace).
- No new phpcs sniff or other automated guard against future raw superglobal use — reviewed manually, matching the framework repo's own choice for the same trade-off.
- No behavior change to nonce verification, filter results, currency resolution, or any other downstream logic beyond the input-reading layer itself.

## Decisions

**0. `Request`/`request()` is used only where a call site is guaranteed to run inside a dispatched request, and only for single-key reads. `Superglobals` is used everywhere else.**

`request()` resolves `app('request')`, which is only ever bound by `Route::dispatch_site()` (site pages) and the REST dispatch path (`get_resolved_request()`/`expose()`). Outside those two boundaries, nothing binds it — calling `request()` there would resolve nothing meaningful. Checked every call site's actual runtime context to classify it:

| Context | Examples | Verdict |
|---|---|---|
| Runs only inside a dispatched site/REST request | `Template::render_pagination/render_category_filter/render_attribute_filters` (called from `shop.php`, `shop/parts/sidebar.php`, and `SiteController`, a REST controller); `shop/single.php`, `shop/parts/empty.php` (site view templates) | `Request`/`request()` eligible |
| Runs outside any dispatched request | `Assets::is_admin_page()` (`admin_enqueue_scripts`), `PageIdentifier` (`display_post_states`, wp-admin filter), `Scheduler::run_async_worker()` (raw `wp_ajax_*`/`wp_ajax_nopriv_*` hook, bypasses the router), `MoneyManager` (called from 38 files including payment-webhook code, no guaranteed request lifecycle) | `Superglobals` only |

Within the "eligible" group, `Request`/`request()` is used **only for single-key reads** (scalar or array) — never as a substitute for "the raw `$_GET` array":
- `Request::all()`/`attributes()` return `array_merge($query, $body, $route_params)` — a merge of query, POST body, and route parameters with no memory of which source a value came from. There is no public "query-only" accessor.
- Two call sites need exactly `$_GET`, undiluted: `Template.php`'s pagination link-rebuilder (`$params = $_GET; ...; http_build_query($params)`) and `shop.php`'s `!empty($_GET)` filter-presence check. Both stay on `Superglobals::query()` — substituting `Request::all()` risks route params or POST fields leaking into a rebuilt URL, or a route-scoped page incorrectly registering as "has filters."
- `Utils::is_nonce_verified()` stays on `Superglobals::post()`/`::query()` even though its only caller (`AuthController`) is a `Route::site()` route (`request()` would resolve there). The current code deliberately reads *only* `$_POST` on a POST request; `Request`'s merged `attributes` has no such method-scoping. Swapping to `request()->text('kecom_nonce')` would let a POST request whose body omits the nonce still pass verification via a stray `?kecom_nonce=...` in the URL — a real, security-relevant loosening of a nonce check, not an equivalent rewrite. Not worth it for a cosmetic win.

**1. `category_ids`/`attribute_value_ids` use `request()->array()`, not `Superglobals`.**
`Request::make_from_http()` merges the raw, unslashed query array into `attributes` with no per-key scalar filtering, so an array value like `category_ids[]=3&category_ids[]=7` survives intact. `Request::get_array()`/`->array()` sanitizes via `Sanitizer::ARRAY`, whose array branch is `if (is_array($value)) { break; }` — a no-op pass-through for an already-array value. So `request()->array('category_ids', [])` returns exactly `['3', '7']`, matching today's `(array)($_GET['category_ids'] ?? [])` output.

Note: `Superglobals::query('category_ids', [], Sanitizer::ARRAY)` also works now — `Superglobals::read()`'s scalar guard gained a `$type !== Sanitizer::ARRAY` exception shortly after this design was written (framework commit `e5a1520`), so the class can no longer do only scalar single-key reads. That doesn't change this decision: `request()->array()` is still used here because Decision 0 already selects `Request` for single-key reads inside a guaranteed request lifecycle, independent of what `Superglobals` can or can't do. The two are equivalent in output for this call site; this was a tie, not a workaround-turned-obsolete.

All view files (`shop.php`, `shop/single.php`, `shop/parts/empty.php`) already `use Kirki\Ecommerce\App\...`-namespaced classes, so adding `use Kirki\Ecommerce\Framework\Http\Superglobals;` / `use function Kirki\Ecommerce\Framework\request;` (and `Sanitizer` where a non-default type is needed) is unremarkable — same autoloader, no new dependency. `request()` is already imported this way in `resources/views/site/login.php`.

**3. `MoneyManager.php` keeps its own `sanitize_text_field()`/`is_string()`/`empty()` guard after the `Superglobals` call.**
`Superglobals::cookie()`/`::server()` already unslash and sanitize via `Sanitizer::TEXT` (= `sanitize_text_field()`) by default, so the existing manual `sanitize_text_field($code)` a few lines later becomes redundant — but harmless, since `sanitize_text_field()` is idempotent. Leaving it in place (rather than trimming it) keeps this conversion mechanical and avoids touching logic adjacent to the actual superglobal read; removing genuinely-dead redundancy here is a separate, smaller cleanup that can happen later if wanted.

**4. `empty.php`'s 7 reads and `single.php`'s `variant_id` read gain sanitization before comparison/casting — accepted, not worked around.**
Today these reads are raw (no `wp_unslash()`, no sanitize) because they're only used in `empty()`/`!==` truthiness checks or an already-casting `(int)`. Routing them through `request()->text($key)`/`request()->int('variant_id', null)` applies `sanitize_text_field()`/an explicit `(int)` cast first (same as today for `variant_id` — `Sanitizer::INT` is a plain `(int)` cast, no behavior change there). For `empty.php`, the only observable difference is on malformed input, e.g. `?sort_by=%20recommended` (leading space) currently reads as "a filter is active" (`' recommended' !== 'recommended'`) and after this change reads as "no filter active" (trimmed to `'recommended'`). This is treated as an acceptable, arguably-more-correct behavior widening rather than a regression to design around — see Risks.

## Risks / Trade-offs

- **`empty.php` filter-presence detection changes for malformed query values with leading/trailing whitespace or stray tags** → Accepted (Decision 4); realistic user-driven query strings are unaffected, and the sanitized comparison is arguably more correct than the raw one.
- **A future contributor could still write `$_GET`/`$_POST` directly, unaware `Superglobals` exists** → Mitigated by documenting the convention in `CLAUDE.md`'s PHP Coding Standards section (not by tooling — matches the scope decision to skip an automated sniff for this change).
- **`libraries/framework/Http/Superglobals.php` is regenerated by `composer scope`, not owned by this repo** → No action needed here; already confirmed in sync with its upstream source. If a future `composer scope` run pulls a version with different semantics, that's a separate concern outside this change.

## Migration Plan

Mechanical, grouped by the table in Decision 1 — no deployment/rollback concerns (pure PHP source change, no schema/data migration, no new runtime dependency). After implementation: `composer phpcs:wporg` and the project's PHP test suite should pass unchanged; the existing `tests/Unit/Supports/UtilsIsAccountPageTest.php` (which sets `$_SERVER['REQUEST_URI']` directly as test fixture data) continues to work unmodified, since `Superglobals::server()` reads from the same live `$_SERVER` array the test mutates.
