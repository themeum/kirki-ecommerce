## Context

`specs/address-book/spec.md` was last touched 2026-09-04. Two later dev commits — `c759e44d` (auto-promote on delete) and `3b8dabb6` (update can set default flags), both 2026-09-10 — changed the behavior the spec describes without updating it. Per direction, newer wins: this change treats those two commits' behavior as authoritative and corrects the spec (see `specs/address-book/spec.md` delta) and `AddressApiTest.php` to match, rather than reverting the code.

`CreateOrderAction::execute()` runs inside its own `DB::begin_transaction()` / `commit()` / `rollback()`. Since dev's address-sync merge, it calls `sync_address()` from inside that transaction, which calls `create_address()` → `AddressService::create()` — a method that opens its *own* `DB::begin_transaction()`. The framework's `Connection::begin_transaction()` (`vendor/libraries/framework/src/Database/Connection/Connection.php`) is a bare `START TRANSACTION` with no depth counter or savepoints, and per MySQL semantics, issuing `START TRANSACTION` while one is already open implicitly commits the pending one first. So the order row inserted moments earlier gets committed early, and a later `throw_if(...)` (e.g. insufficient stock) rolls back nothing — the "failed" checkout leaves an order behind.

`sync_address()`'s own create-vs-use-existing-id logic (if the checkout request already carries a `shipping_id`/`billing_id` — the shopper picked a saved address — use it; otherwise create a new one and mark it default) was confirmed as intentional, current dev design: no change needed to that logic itself.

`addresses.customer_id` is `NOT NULL` and always has been — the address-book model is customer-scoped only. Guest orders intentionally have `customer_id = null` (`specs/checkout-customer-provisioning/spec.md`, "Guest places an order"). Nothing requires a guest order to have an `Address` row; the order's own `shipping_*`/`billing_*` columns are the durable snapshot regardless.

## Goals / Non-Goals

**Goals:**
- Preserve dev's newer address-book behavior (update-can-set-defaults, delete-auto-promotes) exactly as implemented; fix only the actual bug in the update path (omitted default flags getting clobbered to `false`), not the capability itself.
- Stop `sync_address()` from crashing guest checkout and from breaking `CreateOrderAction`'s transaction, without changing its create-vs-use-existing-id decision logic and without modifying `vendor/libraries/framework` (forbidden by CLAUDE.md; the file is regenerated by `composer scope`).
- Keep `AddressService`'s public methods (`create`, `update`, `set_default`) transactional for every *other* caller (the `/account/addresses` endpoints), since those are still standalone top-level operations that need their own atomicity. `delete()` is not, and stays not, transactional (unchanged).

**Non-Goals:**
- No general transaction-nesting/depth-counting mechanism for the whole codebase. Seventeen other call sites open their own `DB::begin_transaction()`, but every one of them is a standalone entry point today — `sync_address()` is the only place a transactional service method is called from inside another already-open transaction. Building a generic nesting-safe transaction manager for a problem with exactly one occurrence would be speculative; if a second occurrence shows up later, generalize then.
- No change to the `addresses` schema (`customer_id` stays `NOT NULL`).
- No change to `sync_address()`'s address-selection logic (use existing id vs. create) — confirmed correct as-is.

## Decisions

### 1. Newer wins on the two behavior-vs-spec conflicts: keep dev's code, fix the spec

**Decision:** `AddressService::delete()`'s auto-promotion (`c759e44d`) is kept unchanged. `AddressService::update()` keeps the ability to accept `is_default_shipping`/`is_default_billing` (`3b8dabb6`), but the bug in how it's implemented is fixed (Decision 2 below). `specs/address-book/spec.md` is corrected via delta to describe both, and `AddressApiTest.php`'s `test_delete_default_address_does_not_promote_another` is rewritten to assert promotion.

**Why:** Both commits post-date the spec by six days and represent a deliberate later design decision, confirmed by direction to treat newer commits as authoritative over stale specs when the two conflict.

### 2. Fix the update-endpoint default-flag bug by distinguishing "omitted" from "false", not by removing the capability

**Decision:** Change `UpdateAddressDTO::$is_default_shipping`/`$is_default_billing` defaults from `false` to `null`. In `AddressService::update()` (and its non-transactional core, see Decision 3), only include `is_default_shipping`/`is_default_billing` in the attributes passed to `$address->update(...)` when the DTO's value is non-null; when either is non-null, still run `unset_current_default()` for that purpose exactly as today.

**Why:** Traced mechanically: `Sanitizer`'s request-to-array traversal (`Sanitizer::traverse_and_sanitize()`) only sets a key when it's present in the raw request (`array_key_exists` check) — an omitted field never appears in `$request->sanitized()`. `DTO::__construct()` only overwrites a property when its key is present in the constructor array — so an omitted field keeps the DTO's class-level default. With that default at `false`, "omitted" and "explicitly false" become indistinguishable by the time `AddressService::update()` sees the DTO, and it was writing both into every update. Moving the default to `null` and skipping `null` at the write step keeps the two cases distinguishable end to end, which is exactly what's needed to keep the newer capability (explicit `true`/`false` still works) while fixing the bug (omitted still means "don't touch").

**Alternatives considered:**
- *Strip the fields from `UpdateAddressDTO`/`AddressUpdateRequest` entirely (my first-pass proposal).* Rejected after clarification — this would remove the capability dev added on 2026-09-10, not just fix the bug in it.
- *Have the frontend always send the address's current default flags on every `PUT`.* Rejected — moves a backend correctness concern into every future API consumer, and doesn't fix the API contract itself.

### 3. Transaction nesting: split `AddressService`'s transactional methods into a public wrapper and a non-transactional core

**Decision:** For `create()`, `update()`, and `set_default()`, extract the existing method body (minus the `DB::begin_transaction()`/`commit()`/`rollback()` wrapper) into a new method (e.g. `create_without_transaction()`), and have the public method be a thin wrapper: open the transaction, call the without-transaction method, commit, catch/rollback. `CreateOrderAction::create_address()`/`update_address()` (both already only called from inside `sync_address()`, itself always inside `CreateOrderAction`'s own transaction) call the `_without_transaction` variants directly instead of the public methods.

**Correction during implementation:** the `_without_transaction` methods had to be `public`, not `protected` as originally written here — `CreateOrderAction` is a separate, unrelated class, and PHP's `protected` visibility is only reachable from the declaring class and its subclasses, not from another collaborator class. Everything else about the decision (the split itself, which methods get it, which callers use which variant) is unchanged.

**Why:** Minimal, surgical fix: it changes nothing about the public `AddressService` API or its behavior for the `/account/addresses` endpoints (still fully transactional, same as today), and it doesn't touch the vendor framework. It directly targets the one real call site that nests.

**Alternatives considered:**
- *Add a depth counter / reference-counting `DB::transaction()` helper at the app layer, used everywhere.* Rejected for now as over-engineering for a single occurrence (see Non-Goals) — but noted as the natural next step if a second nesting call site turns up.
- *Have `CreateOrderAction` not wrap its own steps in a transaction at all.* Rejected — this is a bigger behavior change (order-item inserts, stock reservation, and coupon usage increments all need to roll back together on failure) than the actual bug warrants.
- *Wrap `sync_address()`'s address writes in a `SAVEPOINT`.* Rejected — `Connection` doesn't expose savepoint primitives today, and adding them means touching the vendor file (forbidden) or a parallel raw-SQL savepoint call, more surface area than just not nesting.

### 4. `sync_address()` gets only two changes: a guest guard and non-transactional calls

**Decision:** Add an early return in `sync_address()` when `empty($order->customer_id)`. Change its calls into `AddressService` (via `create_address()`/`update_address()`/`set_default()`) to the `_without_transaction()` variants from Decision 3. No change to which branch (create vs. use existing id) it takes.

**Why:** Confirmed by clarification that the create-vs-use-existing-id logic is dev's intended design, not a bug — a checkout that references an existing saved address (by id) marks it default; a checkout with no address id creates a new one. `update_address()` staying unused is a pre-existing, deliberate consequence of that design, not something this change needs to touch.

### 5. Two more bugs found during implementation, outside the original scope, fixed rather than deferred

**Correction during implementation:** while verifying `OrderApiTest` and the full suite (tasks 4.4-4.5, 7.1a), two more concrete bugs surfaced that weren't part of the original diagnosis:

- `CartService::create_cart()` unconditionally did `$customer->get_shipping_address()['id']` once `!empty($customer)` — but the `customer()` helper always returns a non-null wrapper object, so that guard never skips anything, and for any authenticated user's very first cart (no `Customer` row yet), `get_shipping_address()` returns `null`, and indexing into `null` raised a notice this test environment escalates into a 500. Fixed by guarding on `$customer->get_customer_id()` instead, and null-checking each address before indexing — the resulting values are identical to before for every case, just without dereferencing null. This is the same dev commit (`6a8bd7c9`) this whole change is otherwise fixing, so it's in scope, not scope creep.
- `RemoveCouponAction::execute()` had a merge-conflict-resolution mistake: the merged code kept the multi-coupon branch's structure (`$applied_coupon = $cart->coupons->first(...)`) but the guard clause checked `$applied_coupon_info` — a variable from dev's alternate version of this method that was never assigned in the merged result, so removal always 422'd. Fixed by correcting the guard to check `$applied_coupon`, confirmed against the pre-merge multi-coupon branch's version via `git diff d846797d^1 d846797d^2 -- app/Actions/Cart/RemoveCouponAction.php`.

**Why fixed here rather than filed separately:** both are direct fallout of the same `dev`-into-`chore/multi-coupon` merge this change exists to clean up, both were caught by the same full-suite verification this change's tasks already called for, and both are one-line, unambiguous fixes (a wrong guard condition and a wrong variable name) rather than open design questions.

The customer-contact "Fallback"/"John" mystery from the original proposal (Open Questions, below) is also resolved this way — see tasks.md group 6 for the full mechanism. It was never a WP-user or current-user resolution issue.

## Risks / Trade-offs

- **[Risk]** The `_without_transaction` split could drift out of sync if someone edits the public method later without noticing the protected core is shared. → **Mitigation:** keep the public method's body to just the transaction wrapper + a single call to the protected method, so there's nothing to duplicate or drift.
- **[Risk]** Other callers of `AddressService::create()`/`update()`/`set_default()` might exist outside `CreateOrderAction` and `AddressController` that we haven't audited. → **Mitigation:** proposal.md calls for re-running the *full* `composer run test:docker` suite after the fix, not just the previously-failing tests, specifically to catch this.
- **[Risk]** Changing `UpdateAddressDTO`'s defaults to `null` could affect other code reading those two properties expecting a `bool`. → **Mitigation:** grep for other readers of `UpdateAddressDTO::$is_default_shipping`/`$is_default_billing` during task 2 before shipping; `AddressService::update()` is currently the only one.

## Open Questions

_None remaining. The `test_order_customer_contact_falls_back_to_billing_for_missing_wp_fields` question below was resolved during implementation._

**Resolved:** the `'John'` instead of `'Fallback'`/`'Guest'` failures (three tests, not just one) had nothing to do with WP user profiles or current-user resolution. `OrderCreateRequest::filters()` never listed `is_billing_same_as_shipping`, so the sanitizer dropped the value `rules()` had merged in, and `CreateOrderPayloadDTO`'s own default (`true`) won every time — which made `resolve_billing_and_shipping_addresses()` copy `shipping_first_name` (test fixture default: `'John'`) over each test's `billing_first_name` override before contact resolution ever ran. Fixed at the source (`OrderCreateRequest::filters()`) plus the three affected tests now explicitly set `is_billing_same_as_shipping: false`. See tasks.md group 6.
