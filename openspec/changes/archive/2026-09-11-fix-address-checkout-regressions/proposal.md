## Why

Merging `dev` into `chore/multi-coupon` combined two address-related features that never talked to each other: the multi-coupon branch's guest-checkout-without-a-customer path, and dev's address-book work. Running the full docker suite after the merge surfaces 63 failures / 9 errors (out of 570 tests). Investigation traced them to five distinct causes.

Two of the checked-in specs (`specs/address-book/spec.md`, `specs/checkout-customer-provisioning/spec.md`) were last touched 2026-09-04, but the address-book behavior changed again on dev on 2026-09-10 (`c759e44d` added auto-promotion on delete, `3b8dabb6` let the update endpoint set default flags) — six days *after* those specs were written. The specs are stale on those two points, not the code: this proposal keeps dev's newer behavior and updates the specs to match, rather than reverting the code to the older spec text. The rest of the failures (guest checkout crashing on the address-book's `NOT NULL customer_id`, a nested-transaction bug that lets a failed checkout's order survive, and two tests calling a since-renamed cart method) are genuine bugs regardless of which branch's intent wins — no version of either branch's intent wants a 500 on guest checkout or an order that "failed" to stay in the database.

## What Changes

- **`AddressService::update()` keeps the ability to set default flags (dev's newer capability), but stops clobbering them when omitted.** `UpdateAddressDTO::$is_default_shipping`/`$is_default_billing` currently default to `false`, and the framework's DTO/Sanitizer layer only sets a property when the request actually included that key — so an omitted field and an explicitly-`false` field are indistinguishable once they hit `AddressService::update()`, which always writes both into `$address->update(...)`. **BREAKING (bugfix):** change both DTO properties' default to `null`; `AddressService::update()` only includes `is_default_shipping`/`is_default_billing` in the write when the DTO value is non-null. Result: explicitly submitting `true` or `false` still sets the flag (the capability dev added stays); omitting it leaves the address's current default status untouched (fixes the bug — matches `AddressApiTest.php`'s existing, unmodified `test_update_address_does_not_change_default_status`, which sends no default flag at all and expects it preserved).
- **`AddressService::delete()` keeps auto-promoting a new default (dev's newer behavior) — the spec and test are updated to match, not the code.** `specs/address-book/spec.md` currently says deleting a default address should leave that purpose with no default; that's the pre-`c759e44d` behavior. The spec delta and `AddressApiTest.php`'s `test_delete_default_address_does_not_promote_another` are updated to describe and assert promotion instead.
- **`CreateOrderAction::sync_address()` no longer breaks guest checkout, and no longer breaks the order's transaction.** Its existing logic — use the request's `shipping_id`/`billing_id` when the shopper picked an existing saved address, otherwise create a new one and mark it default — is correct and unchanged (per clarification: sync_address's create-vs-use-existing-id behavior is dev's intended design, not a bug). Two real bugs are fixed:
  1. It's called unconditionally, including for guest orders with no `customer_id` — `create_address()` then tries to `INSERT` an `Address` row with `customer_id = null`, which violates `addresses.customer_id NOT NULL` and 500s. Fix: skip `sync_address()` entirely when `$order->customer_id` is empty.
  2. `AddressService::create()`/`update()`/`set_default()` each open their own `DB::begin_transaction()`/`commit()`. The framework's `Connection` has no nesting support (`begin_transaction()` is a bare `START TRANSACTION`), so calling any of them from inside `CreateOrderAction`'s already-open transaction causes MySQL to implicitly commit the outer transaction early — a subsequent failure (e.g. insufficient stock) then rolls back nothing, and the "failed" order is persisted anyway. Fix: `sync_address()`'s address writes run through new non-transactional internal methods instead, while the public `AddressService` methods keep their own transaction for every other (non-nested) caller. **We do not edit `vendor/libraries/framework/src/Database/Connection/Connection.php`** — see Impact.
- **Two `OrderApiTest.php` tests are updated to use the current cart API.** They call `CartService::add_item(AddToCartDTO)` directly — a public method dev's cart refactor removed in favor of `AddToCartAction::execute(AddToCartDTO)` → `CartService::add_item_to_cart(CreateCartItemDTO)`. `CartApiTest.php` already exercises the new API; these two tests are updated to match instead of calling a method that no longer exists.
- **One `order-customer-contact` test failure needs a live debugging pass, not a blind fix.** `test_order_customer_contact_falls_back_to_billing_for_missing_wp_fields` expects a freshly-factory-created WordPress user to have no `first_name`, but the resolved value is `'John'` even run in isolation. Static reading of `wp_insert_user()`, this plugin's hooks, and the test stubs didn't find the source — this needs a debugger/var_dump pass during implementation. Flagged as a task rather than guessed at here.

## Capabilities

### New Capabilities

_None._

### Modified Capabilities

- `address-book`: "Customer can update an existing address" now allows explicitly setting `is_default_shipping`/`is_default_billing` via `PUT` (previously forbidden); "Customer can delete an address" now promotes another of the customer's remaining addresses to default for whichever purpose the deleted address held (previously left that purpose with no default). Both changes make the spec match dev's newer, already-merged behavior.

## Impact

- **Code:** `app/Actions/Order/CreateOrderAction.php` (`sync_address()` guard + non-transactional calls only — its create-vs-use-existing-id logic and `create_address()`/`update_address()` signatures are unchanged), `app/Services/AddressService.php` (`update()`'s null-handling, and a new non-transactional internal path for `create`/`update`/`set_default`; `delete()` is unchanged), `app/DTO/Address/UpdateAddressDTO.php` (defaults only).
- **Tests:** `tests/Integration/OrderApiTest.php` (2 tests updated to the current cart API, 1 test needs a debugging pass), `tests/Integration/AddressApiTest.php` (`test_delete_default_address_does_not_promote_another` rewritten to assert promotion; `test_update_address_does_not_change_default_status` unchanged — it already asserts the behavior this fix restores).
- **Explicitly not touched:** `vendor/libraries/framework/src/Database/Connection/Connection.php` — per project convention this vendor file is regenerated by `composer scope` from the upstream `themeum/framework` package and any local edit is lost on the next `composer install`. The transaction-nesting fix is done entirely at the application layer (`app/Services/AddressService.php`).
- **Database:** no schema/migration changes. `addresses.customer_id` stays `NOT NULL` — guest checkout is fixed by not attempting to write an `Address` row at all, not by relaxing the column.
- **Risk:** the transaction-nesting fix touches the one code path (checkout) that writes both an `Order` and an `Address` in the same request, so it's worth re-running the full `composer run test:docker` suite (not just the previously-failing tests) after the fix, to catch any other caller that nests into a transactional `AddressService` method the same way.
