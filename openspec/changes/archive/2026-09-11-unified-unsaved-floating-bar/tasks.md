## 2. One navigation guard

- [x] 2.1 In `resources/app/hooks/use-unsaved-navigation-guard.ts` rename the returned `discardChanges` to `proceedNavigation` and `dismissToast` to `cancelNavigation`, leaving the `isSavingRef`, `shakeSignal` bump, and `isBlocked && !isDirty → blocker.reset()` logic and their comments intact.
- [x] 2.2 Add `useEffect(() => { setUnsavedDataStatus(isDirty); return () => setUnsavedDataStatus(false); }, [isDirty])` to the hook so it is the single owner of the global unsaved flag.
- [x] 2.3 Delete `resources/app/features/bulk-edit/hooks/use-bulk-edit-navigation-guard.ts` and point `features/bulk-edit/pages/bulk-edit.tsx` at the shared hook, keeping its own `ConfirmationDialog` and `Badge` UI and dropping its private `beforeunload` listener.
- [x] 2.4 Verify `floating-components/unsaved-tracker.tsx` is untouched and its `beforeunload` still fires for bulk edit through the shared flag.
- [x] 2.5 Route the plugin's own WordPress admin menu clicks through the router in `app.tsx`, so the guard can refuse them. The menu's hrefs are bare hash changes on the current document (`admin.php?page=kirki-ecommerce#/orders`), and the handler assigned `window.location.href` directly — React Router 7 listens only to `popstate`, never `hashchange`, so it saw nothing to block. Its own source warns this "will fail silently in production". Added a local `getInAppPath` that returns the route path when the href is the same document, and handed that to `router.navigate` instead; the menu highlight is now applied after the navigation settles rather than optimistically, so a refused click leaves the current item highlighted. Menu entries outside the plugin, and modifier-clicks that open a new tab, are untouched and still fall through to `window.location`/`window.open`.
