## Context

See `proposal.md` - Why for the motivation. The relevant current code:

- `RecalculateCartAction::build_item_result()` (`app/Actions/Cart/RecalculateCartAction.php:333-358`) sets `$item_result->base_subtotal = $net_total_money->getMinorAmount()->toInt();` unconditionally — `$net_total_money` is just `base_unit_price * quantity` (the raw catalog price), never adjusted for tax. It also computes `$product_total_money = Money::of_minor($item->base_product_total)->multipliedBy($item->quantity);` (the regular-price total used for strikethrough pricing) the same unadjusted way. Only `base_total` (the final charged amount) branches on `$is_inclusive_tax` (tax added on top, or not). So `base_subtotal` and the regular-price total are numerically identical under both settings, but under tax-inclusive pricing that number already has tax embedded in it (the catalog price itself is meant to be read as tax-inclusive), and under tax-exclusive pricing it doesn't.
- `RecalculateCartAction::calculate_item_taxable_amount()` computes tax on the **post-discount** amount (`net_total_money - discount_money`); `build_item_result()` computes `base_subtotal` **pre-discount**. Discount is subtracted later, at the resource layer (`OrderResource::get_items_subtotal()`, `OrderCalculationResource::get_items_subtotal()`, `CartResource::get_items_subtotal()`), all of which do `item->base_subtotal - product_coupon_discount`. This split must be preserved — `base_subtotal` stays pre-discount.
- `CalculationResultDTO::base_subtotal` (order/cart root) is `array_sum` of the per-item `base_subtotal` values (`RecalculateCartAction.php:413`), and `CreateOrderAction` copies `CalculationItemDTO::base_subtotal`/`CalculationResultDTO::base_subtotal` straight onto `OrderItem`/`Order` (`base_subtotal`, `invoiced_subtotal` on both). So the fix in `build_item_result()` (plus the resulting `array_sum`) is the single source of truth for `CartResource`, `OrderCalculationResource`, and `OrderResource`/`OrderItem` storage alike for the subtotal — there is no second write path to fix.
- `CreateOrderAction::prepare_order_item_dto()` (`app/Actions/Order/CreateOrderAction.php:699-753`), separately from the subtotal, sets `OrderItem.base_price`/`invoiced_price` and `base_regular_price`/`invoiced_regular_price` by reading `$variant->base_sale_price ?: $variant->base_price` and `$variant->base_price` **directly from the variant model** — not from the calculated item at all. `UpdateOrderAction::prepare_order_item_dto()` (`app/Actions/Order/UpdateOrderAction.php:385-409`, used when an admin adds a new line item to an already-placed order) duplicates this exact same pattern, reading the variant directly rather than the `$calculated_item` it's already given. (`UpdateOrderAction::prepare_update_order_item_dto()`, used when re-quantifying an item already on the order, is different and correct as-is: it copies the existing item's already-frozen `base_price`/`invoiced_price`/`base_regular_price`/`invoiced_regular_price` forward unchanged, matching `order-item-regular-price`'s "frozen against later changes" requirement — no fix needed there.) Confirmed by searching every `new CreateOrderItemDTO()` call site in the codebase (`app/`): these two `prepare_order_item_dto()` methods are the only two. Both read raw catalog unit prices with the exact same tax ambiguity as the old `base_subtotal`, and today they feed the strikethrough comparison (`OrderResource::prepare_strikethrough_price()`: `$item->base_regular_price > $item->base_price`) and the "only a sale is active" strikethrough amount (`$regular_price_amount * $item->quantity`). Left unfixed on either path, that strikethrough amount would stay tax-ambiguous while the subtotal next to it becomes tax-exclusive — an inconsistency inside the same API response.
- A third resource reads these same `OrderItem` columns: `app/Resources/Site/Order/OrderResource.php` (the **storefront** order-details/order-history payload, distinct from the admin `app/Resources/Order/OrderResource.php` this proposal otherwise refers to as "`OrderResource`"). It renders `invoiced_subtotal`/`invoiced_regular_price`/`invoiced_price` the same way the admin one does (including its own `prepare_strikethrough_price()`, same shape). Decision: frozen like `CartResource` for this change — see Decisions.
- `AbstractTaxStrategy::calculate_tax_amount()` (`app/Tax/Strategies/AbstractTaxStrategy.php:68-77`) confirms the extraction is a straight per-line percentage: `tax = base_amount × rate/(100+rate)` (inclusive) computed against whatever `$base_amount` the country strategy passes for that line — for an item's own tax lines, that base amount is always the item's own taxable amount (`RecalculateCartAction::build_tax_context()` builds one `TaxableItemDTO` per item, taxed independently of other items). This means `tax_amount_money / taxable_amount`, computed once per item in `build_item_result()`, is the item's *exact* combined extraction fraction — correct even when a country strategy applies more than one simultaneous rate to the item, since summing each line's independent extraction against the same base and then dividing by that base reconstructs the combined fraction exactly (no compounding/tax-on-tax exists in this codebase's strategies). This fraction is safe to reapply to any other amount taxed at the same rate composition — the unit price, the regular unit price, and the regular-price total — since discount and tax rate are independent (discount changes the taxable base, not the rate).

## Goals / Non-Goals

**Goals:**
- Every price the calculation engine derives for a line item — subtotal, regular-price (strikethrough) total, unit price, regular unit price — always means "excludes tax," on every new order and cart calculation, regardless of the tax-inclusive-pricing setting.
- The final amount charged (`base_total`/`invoiced_total`) is bit-for-bit unchanged by this fix — only how each price is decomposed changes.
- No inconsistency between the fixed figures: a strikethrough price is never shown in a different tax mode than the subtotal it's paired with, and a unit price is never ambiguous while the subtotal derived from it is not.
- `CartResource`'s output (every field, every value) is unchanged for callers, under both tax settings.
- The storefront `app/Resources/Site/Order/OrderResource.php`'s output (every field, every value) is likewise unchanged for callers, under both tax settings.
- `OrderCalculationResource` loses its `display_*` currency projection and gains the same exclusive/inclusive pairs the admin `OrderResource` gets.
- Wherever a strikethrough figure's inclusive amount can be computed by direct addition of an engine-recorded tax total (i.e. its base is one the engine already tags with its own tax — the item's regular-price total), it SHALL be, instead of reconstructed by rate at every read site — one computation in the engine, reused by all four resources.

**Non-Goals:**
- Not migrating/backfilling existing orders or carts (project is pre-release).
- Not wiring up a shopper-facing storefront toggle for `tax.is_enabled_display_inclusive_taxed_price` — this change makes the underlying data trustworthy and exposes both figures on the admin resources; consuming that setting to pick which one the storefront (cart or order-history) shows is separate, follow-on frontend work. Confirmed with the user: the storefront order-details resource is frozen (same as `CartResource`), not given the dual-field treatment, in this change.
- Not adding exclusive/inclusive figures to shipping or the final order total — those aren't ambiguous today (shipping already reports a net amount plus its tax as a breakdown line; the final total is definitionally the tax-inclusive amount charged).
- Not changing `CartResource`'s own product-price display (`product.display_price_money_object`/`display_sale_price_money_object`), which reads straight from the `Variant` model rather than the calculation engine — untouched, same as today, since `CartResource`'s shape is explicitly frozen for this change.

## Decisions

### How `base_subtotal` and the regular-price total exclude tax under tax-inclusive pricing

`build_item_result()` already computes, per item: `$net_total_money` (pre-discount catalog total), `$discount_money`, and `$tax_amount_money` (tax on the post-discount taxable amount, extracted proportionally when `$is_inclusive_tax` is true — see `AbstractTaxStrategy::calculate_tax_amount()`). To turn `base_subtotal` into a true net figure while keeping it pre-discount (required — the resource layer subtracts discount from it separately), extract tax from `$net_total_money` using the same effective rate the tax strategy already computed for the discounted taxable amount:

```
taxable_amount = net_total_money - discount_money   (already computed)
tax_fraction    = tax_amount_money / taxable_amount   (0 when taxable_amount is 0)
base_subtotal   = net_total_money - (net_total_money * tax_fraction)   // only when is_inclusive_tax
                = net_total_money                                       // when !is_inclusive_tax (unchanged)
```

The same `tax_fraction` — computed once per item — is reused (not recomputed) for the regular-price total: `base_product_total_exclusive = base_product_total_input - (base_product_total_input * tax_fraction)`, applied to the per-unit regular price before it's multiplied by quantity.

This reuses the tax amount the strategy already produced instead of invoking the tax strategy a second time against a different taxable base — cheaper, and it can't disagree with the tax actually charged. See Context for why the same fraction is valid to reapply to the regular-price total (and, below, to unit prices) even under multi-line tax strategies.

**Alternative considered**: re-run the tax strategy on the pre-discount amount and on the regular-price amount to get their own "true" tax, and subtract those directly. Rejected — multiplies the number of tax-strategy calls per item per calculation, and risks disagreeing with the tax actually charged under a country strategy whose line count depends on the taxable amount (e.g. threshold-based rates), producing figures inconsistent with `base_total`.

### `CalculationItemDTO` gains a tax-excluded regular unit price; unit price is fixed in place

Every field this action derives is tax-exclusive after this change — there's no stored "inclusive" counterpart anywhere in the DTO, only a derived one at the resource layer (see `item-pricing-tax-exclusivity`). So these don't get an `_exclusive` suffix; they're fixed the same way `base_subtotal`/`base_product_total` already are, in place, using the same `tax_fraction` as above, applied to the *per-unit* catalog prices before they're scaled by quantity or reduced by discount:

- `base_unit_price` — overwritten in place on the cloned item (no new field: nothing downstream reads `CalculationItemDTO::base_unit_price` after `build_item_result()` runs, so this is safe, same as `base_subtotal`).
- `base_regular_unit_price` — a genuinely new field, since today nothing on the output holds the regular price per-unit (only `base_product_total`, which `build_item_result()` overwrites with the regular-price *total*). Set from `$item->base_product_total` (the input, still per-unit at that point in the method, before the multiply).

`CreateOrderAction::prepare_order_item_dto()` **and** `UpdateOrderAction::prepare_order_item_dto()` both read these two fields (converting to the order's invoiced currency the same way each already does for `base_subtotal`) instead of re-reading `$variant->base_sale_price`/`base_price` directly, for `OrderItem.base_price`/`invoiced_price`/`base_regular_price`/`invoiced_regular_price`. This makes `RecalculateCartAction` the single place tax-exclusivity is decided, and both order-item write paths pure copiers of its output — the same pattern the subtotal already follows on both paths today.

**Alternative considered**: leave unit-price extraction to `CreateOrderAction` itself, reading `$variant`'s raw prices and a tax-fraction value exposed alongside the calculated item. Rejected — splits the extraction formula across two classes for no benefit, and risks the two call sites' formulas drifting apart over time.

### Deriving an inclusive figure from a different base: the rate multiplier

Adding an item's dollar `tax_total` to its exclusive subtotal is exact **only** because both were computed against the same (post-discount) taxable base. A strikethrough figure is a *different* base — the pre-discount subtotal, or the pre-sale regular-price total — that was never itself taxed, so adding the charged item's `tax_total` to it would misstate the result (a larger base should carry proportionally more tax, not the same dollar amount). The correct derivation scales by the item's effective tax rate instead:

```
rate_fraction = current_price_tax / current_price_exclusive   // reconstructed from already-exposed fields, no new storage
inclusive_strikethrough = exclusive_strikethrough + (exclusive_strikethrough * rate_fraction)
```

**Correction during implementation**: the original version of this decision branched on `is_inclusive_tax` (mirroring the engine-side extraction formula's two modes). That branch turned out to be unnecessary at the resource layer. `AbstractTaxStrategy::calculate_tax_amount()`'s two modes exist because the engine has to extract tax from a mode-*ambiguous* raw catalog figure (gross under one setting, net under the other). The resource layer never touches that raw figure — by the time a resource runs, `item-pricing-tax-exclusivity` guarantees `current_price_exclusive` (and the strikethrough's own exclusive figure) are *already* net, unconditionally, regardless of which mode produced them. Going from a known-net amount to its gross equivalent at a given rate is a single, mode-independent operation: `gross = net + net × (tax / net)`. So `current_price_exclusive` and `current_price_tax` (the item's own current-price exclusive amount and its recorded tax — already computed for the current-price money objects) are all `prepare_strikethrough_price()` needs; no `is_inclusive_tax` parameter, and no branch. This is still the exact algebraic relationship extraction produces (verified in Context to hold even for multiple simultaneous tax lines on one item), just simpler once both sides are already net.

### The regular-price total's own tax is computed once by the engine and stored, not re-derived by rate at every read site

**Follow-up decision, added after the rest of this change had already shipped.** The rate-multiplier derivation above (`inclusive_strikethrough = exclusive_strikethrough + exclusive_strikethrough × rate_fraction`) is correct, but every one of the four resources (`OrderResource`, `OrderCalculationResource`, `CartResource`, storefront `OrderResource`) reconstructs `rate_fraction` independently at read time from the item's current-price exclusive amount and tax — the same computation, duplicated four times, for what is usually the exact same underlying question: "what's the tax on this item's regular-price total?"

`RecalculateCartAction::build_item_result()` already computes the regular-price total as an exact, tax-exclusive `Money` value (`$product_total_money`, assigned to `$item_result->base_product_total`) before this change even shipped. Since that amount's own tax is now computable at the same place, for the same reason `base_tax_amount` is: a new helper, `calculate_regular_tax_amount(array $tax_lines, Money $exclusive_regular_total_money)`, sums `$exclusive_regular_total_money × (line.rate / 100)` (`RoundingMode::HALF_UP`) per tax line — the same "exclusive-basis, tax added on top" formula `AbstractTaxStrategy::calculate_shipping_tax_amount()` already uses for shipping, appropriate here because `$exclusive_regular_total_money` is, after this change, always already net. The result is stored on `CalculationItemDTO::$base_regular_tax_amount`, then persisted the same way `base_tax_amount` already is: `OrderItem.base_regular_tax_total`/`invoiced_regular_tax_total`, written by both `CreateOrderAction::prepare_order_item_dto()`/`UpdateOrderAction::prepare_order_item_dto()` (new items) and `UpdateOrderAction::prepare_update_order_item_dto()` (re-quantified items, sourced from the recalculated item, matching how `base_tax_total` is already sourced there rather than frozen from the existing row).

**Why this doesn't eliminate `derive_inclusive_amount_at_rate()`.** A strikethrough amount is one of exactly three things, decided by each resource's existing `prepare_strikethrough_price()` branching (unchanged by this decision):

1. The item's regular-price total (on sale, no item-level coupon) — shares `base_regular_tax_total`'s base exactly.
2. The item's subtotal before an item-level coupon discount, on an item that is **not** on sale — since `base_price == base_regular_price` when there's no sale, this pre-coupon subtotal is numerically the item's regular-price total too, so it *also* shares `base_regular_tax_total`'s base exactly, even though it arrived at that base via a different code path (the coupon branch, not the sale branch).
3. The item's subtotal before an item-level coupon discount, on an item that **is** on sale (sale and item-coupon compounding) — this pre-coupon subtotal is at the *sale* price, not the regular price, so it does **not** share `base_regular_tax_total`'s base. No stored figure matches this case's base; only the rate-multiplier derivation is exact here.

So each `prepare_strikethrough_price()` compares the chosen `$strikethrough_amount` against the item's regular-price total (`base_regular_price × quantity` in the two order resources / `calculated_item->base_product_total` in `CartResource`/`OrderCalculationResource`, which already *is* that total): equal → add `base_regular_tax_total`/`invoiced_regular_tax_total`/`calculated_item->base_regular_tax_amount` directly (cases 1 and 2, the common ones); not equal → fall back to `derive_inclusive_amount_at_rate()`, unchanged (case 3, the compounding edge case). `derive_inclusive_amount_at_rate()` stays in all four resources — it is still the only correct derivation for case 3, not dead code.

**Alternative considered**: also compute and store a second field for case 3's base (tax on the pre-coupon subtotal at whatever the item's current price happens to be), eliminating `derive_inclusive_amount_at_rate()` entirely. Rejected (user's explicit call) — that base isn't naturally engine-computable the way the regular-price total is: which discounts are "item-level coupon" versus other discount sources is a persisted-`OrderCoupon`/`OrderItemCoupon` concept resolved at the resource layer (`find_product_coupon_discounts_for_item()`), not something `RecalculateCartAction`'s flat per-item discount total distinguishes internally. Threading that distinction into the engine to serve one rare compounding case is a materially bigger change than what was asked for; the existing rate-multiplier derivation already handles it exactly.

### Strikethrough price consistency (order resources)

Since the subtotal now has two representations (exclusive/inclusive), the strikethrough "was" price must too, or a UI showing the tax-inclusive subtotal next to an exclusive-only "was" price would show a nonsensical comparison. `OrderResource::prepare_strikethrough_price()` and `OrderCalculationResource::prepare_strikethrough_price()` each return two money objects (exclusive/inclusive) instead of one: the exclusive figure is the (now tax-excluded) `base_subtotal`/`base_product_total`-derived amount, unchanged from today's single figure; the inclusive figure is always computed by the rate-fraction formula above — both figures are exposed unconditionally, regardless of the store's tax-inclusive-pricing setting (that setting only mattered inside the engine's extraction step; a resource never needs to branch on it).

For the **root** `items_subtotal`/`order_total` figures, the tax to reconstruct their inclusive counterpart is the sum of every item's own recorded tax (`items_tax_total`, computed alongside `items_subtotal` - **not** the order's own `invoiced_tax_total`/`base_tax_total` model field, which also includes shipping tax and would overstate the items-only inclusive figure).

### `CartResource` stays output-stable by adding tax back only where its old output was gross, not by reading two figures

`CartResource::prepare_items()` / `get_items_subtotal()` currently render `calculated_item->base_subtotal` directly as the shopper-facing price, and `prepare_strikethrough_price()` reads `calculated_item->base_product_total` directly for its "only a sale is active" branch. Before this change, both of those raw figures were **gross under tax-inclusive pricing and net under tax-exclusive pricing** (the same ambiguity `item-pricing-tax-exclusivity` fixes) - so `CartResource`'s pre-fix output already implicitly matched the store's own tax-display convention: gross when priced inclusive, net when priced exclusive. After the engine fix, both are always net. To keep `CartResource`'s output pixel-identical to before (per proposal), it must reproduce that same mode-dependent choice - unlike the order resources above (which always expose both figures), `CartResource` must still know `is_inclusive_tax` to decide *whether* to apply the rate-fraction formula at all, not just how:

- Subtotal: under tax-inclusive pricing, render `base_subtotal + (base_subtotal × base_tax_amount / base_subtotal)` = `base_subtotal + base_tax_amount` (exact here, since subtotal and its own tax share the same base); under tax-exclusive pricing, render `base_subtotal` unchanged.
- Strikethrough ("only a sale is active" branch, `base_product_total`) and ("coupon applied" branch, `base_subtotal`): under tax-inclusive pricing, apply the rate-fraction formula above using the item's own current-price exclusive amount and tax as the rate source (**not** a flat `+ base_tax_amount` — that base mismatch is exactly the bug this section fixes); under tax-exclusive pricing, render the exclusive amount unchanged.

`CartResource` is an internal consumer of the same derivation formula as `item-pricing-tax-exclusivity`; it just decides per-mode whether to apply it, and never exposes the exclusive figure separately.

**Alternative considered**: give `CartResource` the same flat-sibling exclusive/inclusive fields as the two order resources, and let the frontend pick. Rejected — the proposal is explicit that `CartResource`'s structure and behavior stay as-is; changing its shape is out of scope for this change and would touch the storefront checkout UI, which isn't part of this proposal.

### Storefront order-details `OrderResource` (`app/Resources/Site/Order/OrderResource.php`) stays output-stable, same as `CartResource`

This resource reads the same `OrderItem` columns as the admin `OrderResource` (`invoiced_subtotal`, `invoiced_regular_price`, `invoiced_price`) and has its own `prepare_strikethrough_price()` of identical shape. Confirmed with the user: it is frozen for this change rather than given the dual-field treatment, matching `CartResource`'s precedent rather than the admin `OrderResource`'s. It applies the exact same mode-dependent compensation as `CartResource` (Decisions above), adapted to its invoiced-currency-only shape (it has no `base_*`/`display_*` pair to manage — it already exposes only `invoiced_*`, per `storefront-order-pricing-breakdown`):

- Item subtotal and root `invoiced_items_subtotal`/`invoiced_order_total`: under tax-inclusive pricing, add the item's own `invoiced_tax_total` back (exact — same base); under tax-exclusive pricing, unchanged.
- Strikethrough (`prepare_strikethrough_price()`, both the coupon-applied and sale-only branches): under tax-inclusive pricing, apply the rate-fraction formula (not `+ invoiced_tax_total` — same base-mismatch reasoning as the admin resources' strikethrough); under tax-exclusive pricing, unchanged.

Like `CartResource`, this resource needs `is_inclusive_tax` (the store's tax setting) to decide *whether* to apply the derivation, since it's reconstructing old mode-dependent output rather than always exposing both figures.

This resource has no `OrderCalculationResource`-style counterpart and is not part of either Modified Capability in this proposal (`storefront-order-pricing-breakdown` is left untouched — its existing requirements already describe today's single-figure behavior, which continues to hold numerically as well as structurally).

### `OrderCalculationResource` restructuring

`pricing` → `totals` (matching `OrderResource`'s key), `display_*` fields dropped, `base_*` fields keep their existing names, and the new `*_exclusive_money_object`/`*_inclusive_money_object` siblings are added for item subtotal, item strikethrough price, and root items-subtotal/order-total — the same places `OrderResource` gets them, keeping the two resources' shared shape aligned per the proposal's "modified capabilities" scoping. `available_shipping_methods` and `shipping_method` (calculation-only fields) are unchanged in shape, just lose their `display_cost_money_object` sibling.

## Risks / Trade-offs

- [Risk] `tax_fraction` computed via integer-minor-unit division could introduce off-by-one rounding versus the pre-fix numbers, since `base_subtotal`/unit prices were previously exact integer copies of the catalog price. → Mitigation: perform the fraction/multiply in `Brick\Money` (already used throughout this action) to keep rounding consistent with how `tax_amount_money` itself was rounded, and add unit tests asserting `exclusive + item_tax_total == inclusive == previous (pre-fix) gross value` under tax-inclusive pricing, for subtotal, regular-price total, unit price and regular unit price, so any rounding drift is caught rather than silently accepted.
- [Risk] `taxable_amount == 0` (e.g. a fully-discounted item) makes `tax_fraction` undefined. → Mitigation: special-case it to `tax_fraction = 0`, matching `tax_amount_money` being `0` in that case — the item has no tax to exclude, for the subtotal, the regular-price total, and both unit prices alike (they all reuse the same fraction).
- [Risk] `unit_price_exclusive × quantity` will not always equal `subtotal_exclusive` to the last minor unit, since one is computed by extracting tax from a per-unit amount and the other from the pre-discount line total — two independent roundings of the same proportional relationship. → Mitigation: accept this (money math already tolerates line-total vs. per-unit rounding elsewhere in this codebase); do not attempt to force equality by deriving one from the other via division, which would reintroduce a different rounding hazard. Cover it with a test asserting the discrepancy, if any, is at most one minor unit.
- [Risk] Any existing PHPUnit test asserting `base_subtotal`, `base_product_total`, `base_price`, or `base_regular_price`'s exact value under tax-inclusive pricing will now fail (expected, and called out in the proposal's Impact section) — a missed test site would let a regression through silently. → Mitigation: `tasks.md` includes an explicit sweep of calculation/action/resource tests for tax-inclusive-pricing fixtures, not just the ones already known to touch `base_subtotal`.
- [Risk] The strikethrough rate-multiplier derivation (`1/(1-tax_fraction)` under tax-inclusive pricing) is a division, not a simple addition, and reconstructs `tax_fraction` from the item's own current-price exclusive amount and tax total at render time — a resource that mistakenly reuses the older "+ tax_total" shortcut for strikethrough would silently understate the inclusive "was" price whenever the strikethrough base differs from the current-price base (which is the common case: any sale or coupon). → Mitigation: a unit test per resource asserting the strikethrough inclusive figure is **not** equal to `exclusive_strikethrough + item_tax_total` whenever the strikethrough base differs from the current price, and **is** equal to `exclusive_strikethrough × multiplier` computed independently in the test.
- [Risk] A resource's new "does the strikethrough base equal the regular-price total" comparison could pick the direct-addition path for the sale-plus-coupon compounding case by mistake — e.g. comparing against the wrong amount, or comparing loosely — silently reintroducing the exact base-mismatch bug this change exists to fix, just for `base_regular_tax_total` instead of `base_tax_total`. → Mitigation: compare the exact minor-unit integer amounts (not a tolerance/rounding-aware comparison), and add a unit test per resource specifically for the compounding case (item on sale **and** item-level coupon applied) asserting the result still comes from `derive_inclusive_amount_at_rate()`, not direct addition — i.e. that it's **not** equal to `exclusive_strikethrough + base_regular_tax_total`.
- [Risk] Pre-existing orders (placed before this follow-up ships) have `base_regular_tax_total`/`invoiced_regular_tax_total` default to `0`, same as their `base_price`/`base_subtotal` may already be stale relative to this change's earlier tax-exclusivity fix. → Mitigation: none beyond what the rest of this change already accepts (see proposal.md, "Existing (pre-change) orders/carts are not migrated") — this is the same category of already-signed-off limitation, not a new one; not re-litigated here.

## Migration Plan

`invoiced_regular_tax_total`/`base_regular_tax_total` (int, default `0`) are added to the existing `AlterOrderItemsAddRegularPriceColumns` migration, not a new migration file — the plugin has no tagged release containing that migration yet (confirmed: it postdates `v1.0.0-alpha.4`, the latest tag), so there's no already-shipped migration history to preserve, and the user explicitly chose one file for both purposes over the idempotency-safe default (a new migration, which would be needed once this ships to users who already ran the old version of this migration). No data backfill — pre-release project, existing rows are left as-is per the proposal, same precedent as every other field this change touches.

**Caveat**: any environment that already ran the pre-amendment version of `AlterOrderItemsAddRegularPriceColumns` (e.g. `dev`, other branches, already-migrated local/staging DBs — it's merged into `dev` already) will not automatically pick up the two new columns, since migration frameworks track completion by migration identity, not content; those environments need the migration re-run manually (e.g. drop-and-rerun, or a manual `ALTER TABLE`) after this change lands. Accepted by the user as fine for a pre-release project.

Deploy is a single coordinated release: the calculation-engine fix, both order-item write paths' updated unit-price copying, the amended migration and both write paths' population of the new columns, and all four resources' updated strikethrough derivation must ship together, since `OrderCalculationResource`/`OrderResource` reading the new exclusive/inclusive siblings depends on `base_subtotal`/unit prices already being net, `CartResource`'s and the storefront `OrderResource`'s compensating add-backs depend on it too, and every resource's strikethrough fast path depends on `base_regular_tax_total`/`invoiced_regular_tax_total` being populated. No rollback concern beyond reverting the whole change together.
