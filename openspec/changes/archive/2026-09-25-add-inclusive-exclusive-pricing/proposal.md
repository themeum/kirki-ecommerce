## Why

Order-item and cart-item subtotals are stored ambiguously: `base_subtotal`/`invoiced_subtotal` contains tax or not depending on whatever the global `tax.is_tax_inclusive_price` setting happened to be at calculation time, with no per-order record of which mode produced it. The same ambiguity applies to the unit prices recorded on an order item (`base_price`, `base_regular_price`, `invoiced_price`, `invoiced_regular_price`) and to the regular-price total used for strikethrough pricing — all of them are raw catalog-price snapshots that are gross under tax-inclusive pricing and net under tax-exclusive pricing, with nothing recording which. `OrderResource` and `OrderCalculationResource` both pass these ambiguous figures straight through, so the storefront/admin cannot reliably show a shopper "price including tax" vs "price excluding tax" — the existing (unused) `tax.is_enabled_display_inclusive_taxed_price` setting has no data to switch between — and, left half-fixed, a subtotal made tax-exclusive would sit next to a strikethrough "was" price that's still ambiguous, an internal inconsistency within the same API response. Shipping already avoids this problem (it's always stored gross and displayed net via subtraction); items need the equivalent fix, applied consistently everywhere the store's catalog price is copied onto an order. `OrderCalculationResource` separately carries a `display_*` currency-preview pattern left over from being modeled after `CartResource`, even though it's admin-only and doesn't need a second currency projection.

## What Changes

- **BREAKING**: `CalculationItemDTO::$base_subtotal` and the regular-price total it derives for strikethrough purposes (and the `OrderItem`/`CartItem` `base_subtotal`/`invoiced_subtotal` values copied from it) are now always net-of-tax, regardless of `tax.is_tax_inclusive_price`. Previously these figures were gross under tax-inclusive pricing.
- **BREAKING**: `CalculationItemDTO` gains the tax-excluded unit price and regular unit price for the item, and both order-item write paths — `CreateOrderAction::prepare_order_item_dto()` (new order) and `UpdateOrderAction::prepare_order_item_dto()` (item added to an existing order) — record `OrderItem.base_price`/`invoiced_price`/`base_regular_price`/`invoiced_regular_price` from those instead of copying the variant's raw catalog price — so every price ever written onto an order is net-of-tax, on the same terms as the subtotal, keeping the on-sale comparison (`base_regular_price > base_price`) and reporting queries consistent regardless of which pricing mode was active when the order was placed or edited. (`UpdateOrderAction::prepare_update_order_item_dto()`, which re-quantifies an *existing* item, is unaffected — it already carries the frozen price forward unchanged, per `order-item-regular-price`.)
- `OrderResource`: each item's subtotal and strikethrough price, and the root `items_subtotal`/`order_total`, gain flat sibling `*_exclusive_money_object` / `*_inclusive_money_object` keys (replacing the single ambiguous `*_money_object` key) for both `invoiced_*` and `base_*` — so a strikethrough "was" price is always shown in the same tax mode as whichever "now" price (exclusive or inclusive) it's paired with.
- `OrderCalculationResource`: the same exclusive/inclusive sibling treatment for item subtotal, item strikethrough price, and root `items_subtotal`/`order_total`, computed against `base_*` only.
- **BREAKING**: `OrderCalculationResource` drops all `display_*` fields — it is admin-only (order create/recalculate screen) and never needed a second-currency projection. Its `pricing` key is renamed to `totals` and restructured to mirror `OrderResource`'s nesting for the fields the two resources share; calculation-only fields (`available_shipping_methods`, `shipping_method`) are unchanged.
- **BREAKING**: `OrderItem` gains `base_regular_tax_total`/`invoiced_regular_tax_total`, the tax portion of the item's regular-price total (`base_regular_price`/`invoiced_regular_price` × quantity), computed by the calculation engine at the same time as `base_tax_total`/`invoiced_tax_total`. Every strikethrough/"was" price derivation that used to reconstruct this figure by scaling at the item's effective tax rate (`derive_inclusive_amount_at_rate()`) now adds it directly whenever the strikethrough amount being shown *is* the regular-price total (the common case: item bought on sale with no item-level coupon, or item-level coupon with no sale) — the rate-scaling derivation is kept only for the one remaining case where the strikethrough amount is neither the current price's own base nor the regular-price total (an item-level coupon applied *while the item is also on sale*, where the "was" price shown is the pre-coupon amount at the sale price, not the regular price).
- `CartResource`'s output (fields, values, structure) does not change. It compensates for the now-always-net `base_subtotal` and regular-price total internally — both its subtotal and its strikethrough price — so a tax-inclusive store's storefront cart is unaffected by the storage change.
- `app/Resources/Site/Order/OrderResource.php` (the storefront order-details/order-history payload — distinct from the admin `OrderResource` this proposal otherwise refers to) gets the same treatment as `CartResource`: its output stays unchanged, via the same compensation, so a tax-inclusive store's storefront order page is unaffected by the storage change. It does not gain exclusive/inclusive sibling fields in this change.
- Existing (pre-change) orders/carts are not migrated — the project is pre-release (alpha), so no backfill is required.

## Capabilities

### New Capabilities

- `item-pricing-tax-exclusivity`: defines that every price the calculation engine derives for a line item — its subtotal, its regular-price (strikethrough) total, its unit price, and its regular unit price — is always net-of-tax, independent of the store's tax-inclusive-pricing setting, and that any inclusive-of-tax figure is derived by adding the item's own tax total rather than being stored separately. Covers both the in-request calculation (`CalculationItemDTO`) and what gets persisted onto `OrderItem`.

### Modified Capabilities

- `admin-order-pricing-breakdown`: the admin order payload's item subtotal, item strikethrough price, and root items-subtotal/order-total figures expose both a tax-exclusive and a tax-inclusive money object instead of one ambiguous figure.
- `admin-order-calculation-breakdown`: the manual-order calculation payload drops its display-currency projection (base-currency only, admin-only usage) and gains the same exclusive/inclusive money-object pair as the admin order payload for item subtotal, item strikethrough price, and root items-subtotal/order-total.

## Impact

- **Code**: `RecalculateCartAction::build_item_result()` (and any other writer of `CalculationItemDTO::$base_subtotal`/`$base_product_total`, plus the new unit-price/regular-unit-price/regular-tax fields), `CalculationItemDTO` (new `base_regular_unit_price` and `base_regular_tax_amount` fields), `CreateOrderAction::prepare_order_item_dto()` and `UpdateOrderAction::prepare_order_item_dto()` (both now read the calculated item's tax-excluded unit/regular price instead of the variant's raw price — confirmed the only two `CreateOrderItemDTO` construction sites in the codebase; `UpdateOrderAction::prepare_context_items()` also needed a one-line fix — it never populated `base_product_total` on its input DTO, silently zeroing `base_regular_unit_price` for every item added via an order edit), `UpdateOrderAction::prepare_update_order_item_dto()` (new `base_regular_tax_total`/`invoiced_regular_tax_total` sourced from the recalculated item, same as `base_tax_total` already is there), `CreateOrderItemDTO`/`UpdateOrderItemDTO` (new fields), `OrderItem` model (`$fillable`), `OrderCalculationController.php` (dropped the now-dead `currency_code` pass-through), the admin `OrderResource`, `OrderCalculationResource`, `CartResource` and the storefront `app/Resources/Site/Order/OrderResource.php` (all four: `prepare_strikethrough_price()` gains the direct-addition fast path described above, on top of the compensating/dual-field treatment each already has).
- **Tests**: calculation/action unit tests asserting `base_subtotal`, `base_product_total`, unit price or regular price under tax-inclusive pricing need their expected values updated (net instead of gross), plus new assertions for `base_regular_tax_amount`; resource tests for `OrderResource`/`OrderCalculationResource` need new assertions for the exclusive/inclusive sibling keys (subtotal and strikethrough) and (for calculation) the removed `display_*` keys, plus assertions that the strikethrough fast path returns the exact stored regular-tax figure and that the sale-plus-coupon compounding case still uses rate-derivation; `CartResource`/storefront `OrderResource` tests should additionally assert subtotal and strikethrough totals are unchanged under tax-inclusive pricing after the engine change, including in the compounding case; `tests/Integration/OrderApiTest.php` needs new assertions that `OrderItem.base_regular_tax_total`/`invoiced_regular_tax_total` persist correctly.
- **Frontend**: `resources/app/services/order.ts` and any TypeScript types/consumers reading `OrderCalculationResource`'s `pricing.display_*` fields need updating to `totals.base_*_exclusive_money_object`/`*_inclusive_money_object`; admin order-detail views consuming `OrderResource` money objects need updating to the new sibling keys where they render item/subtotal/strikethrough/total prices. No further frontend impact from the regular-tax-total addition — it changes how the existing exclusive/inclusive keys are computed, not the response shape.
- **DB schema change**: adds `invoiced_regular_tax_total`/`base_regular_tax_total` (int, default 0) to `kirki_ecommerce_order_items`, added to the existing `AlterOrderItemsAddRegularPriceColumns` migration rather than a new migration file — the plugin hasn't been released yet (confirmed: that migration predates any tagged version, so no shipped history to preserve), and the user chose one file for both purposes. No backfill for existing rows — same pre-release/alpha precedent as the rest of this change (see above). An order placed before this ships reads `0` for both new columns, same as it already reads a stale/ambiguous `base_price`/`base_subtotal` today; this is an existing, already-accepted limitation of shipping without a migration, not a new one. Every other value this change touches (`base_subtotal`/`invoiced_subtotal`/`base_price`/`invoiced_price`/`base_regular_price`/`invoiced_regular_price`) is a value change on an existing column, not a schema change.
