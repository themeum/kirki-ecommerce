## Context

See `proposal.md` — Why, for the motivation. The constraints that shape this design:

- **The drift is foreign keys only, and it is total.** Verified by reading `themeum/framework`
  2.1.15 at the commit `composer.lock` pins (`f168281`): `Compiler::compile_foreign()` emits
  `FOREIGN KEY (col) REFERENCES ...` with no `CONSTRAINT` clause, ignoring the name argument
  entirely. So **all 67 foreign keys on an alpha.1 site are engine-named `{table}_ibfk_n`**,
  including the 33 the migrations explicitly name. Conversely 2.1.15's `Structure::index()` and
  `unique()` already produced `{table}_{columns}_index`/`_unique`, `get_table()` returns the
  unprefixed name in both versions, and no unnamed key exceeds 64 characters — so indexes, uniques
  and primary keys are byte-identical across both populations and were never broken.
- **Two of the three existing workarounds were unnecessary.** The `information_schema` lookups for
  the `is_excluded` index and for `idx_customer_carts` were solving a non-problem; only the
  foreign-key lookups were ever needed.
- **Two populations, one source tree.** `Create*` migrations are byte-identical between
  `v1.0.0-alpha.1` and HEAD, and migration history is recorded per class name in a WP option, so
  those classes never re-run on an existing site. Verified against the tag: **no**
  `Alter*`/`Add*`/`Replace*` migration existed at alpha.1, so an alpha.1 database sits in exactly
  post-`Create` state.
- **142 keys across 38 tables**, in four coexisting naming styles
  (`fk_kirki_ecommerce_cart_items_variant_id`, `fk_refunds_order_id`, `idx_fraud_detection`, and
  library-generated).
- **The framework is off-limits.** `themeum/framework` stays at 3.0.3. It is a separate scoped
  package regenerated by `composer scope`, and `libraries/` is gitignored.
- **No portable `IF EXISTS`.** MariaDB supports `IF EXISTS` on `DROP FOREIGN KEY` / `DROP INDEX`;
  MySQL supports neither. Introspection is mandatory, not a convenience.
- **No portable `RENAME INDEX`.** Needs MariaDB 10.5.2+; live WordPress hosts commonly predate it.
  Foreign keys can never be renamed in place on any version.
- **All 38 tables share the `kirki_ecommerce_` prefix** consistently, so table selection and short-
  name derivation have no exceptions.

## Goals / Non-Goals

**Goals:**

- One uniform naming scheme replacing all four current ones.
- A migration that cannot alter schema semantics — only identifiers.
- A guardrail that fails CI when a future migration omits a key name, without requiring a list of
  known migrations to be maintained.

**Non-Goals:**

- Fixing `Compiler::generate_primary()`, which emits a `CONSTRAINT` name MySQL silently discards
  while the alter path emits none. Dead API surface; a separate concern.
- Editing the `Create*` migrations. They keep declaring unnamed keys (see Decision 4).
- Multisite. No `Network:` header and no multisite code exists, so per-site prefix collisions are
  out of scope.
- Any change to application code, REST responses, or the admin UI.

## Decisions

### 1. Rename-only, with names computed rather than transcribed

The migration enumerates each table's live keys, computes the target name from the table, columns
and key type, and re-creates each key from **the definition it read back from the database** —
same columns, same uniqueness, same referenced table/column, same `ON DELETE`/`ON UPDATE` rules.

*Alternative considered: declare all 142 constraints in full inside the migration.* Rejected. It
reads better as a registry, but means hand-transcribing 33 foreign-key definitions including every
delete rule. A dropped `cascade_on_delete()` fails no test — it silently changes production
referential behaviour. Reading the live definition makes that class of error structurally
impossible, and shrinks the migration to roughly 60 lines.

*Alternative considered: a 142-entry name map.* Rejected as a second source of truth that will
drift from the scheme.

### 2. Scheme: `{fk|idx|uq}_{table}_{columns}`

`table` is the table name as it appears after the WordPress prefix, keeping its `kirki_ecommerce_`
namespace. Examples: `fk_kirki_ecommerce_cart_items_variant_id`,
`idx_kirki_ecommerce_carts_customer_id_created_at`, `uq_kirki_ecommerce_products_slug`.

The namespace is retained deliberately: **InnoDB requires foreign-key names to be unique per
database**, and that database is shared with WordPress core and every other plugin. Shortening to
`fk_cart_items_variant_id` would risk a collision that surfaces as a migration failure on a
customer's site.

Carrying the whole namespace rather than a shortened `kirki_` also means the derived name is exactly
what the `Create*` migrations already hand-write (`fk_kirki_ecommerce_order_items_order_id`,
`fk_kirki_ecommerce_products_brand_id`, and 31 more), so the scheme reads as the established
convention rather than a fourth one. The cost is 5 overrides instead of 1 (Decision 3).

*Alternative considered: shorten to `kirki_` by stripping `ecommerce_` from the table.* Rejected on
review — it keeps names under the limit more easily, but introduces a naming style that appears
nowhere else in the codebase, and every existing explicitly-named key would have to change to match.

*Alternative considered: short semantic names* (`idx_fraud_detection`). Rejected — not derivable,
so the guardrail could only assert that *a* name exists, not that it is the right one.

### 3. Names exceeding 64 characters take an explicit override

MySQL's identifier limit is 64 characters. The keys that would overflow under this scheme must be
determined by computing names against a real migrated database, not by parsing migration source —
an earlier source-parse produced a false positive by applying the scheme to keys that are already
explicitly and short-named (`idx_active_coupons`, `unique_attribute_language`). Any genuine overflow
takes a short explicit name from a small override map.

Measured against all 141 keys, 5 overflow: the four-column coupons index, the two translation-table
uniques, and the two three-column orders status indexes. One more — the product-translations unique
— lands on exactly 64 and is left alone. The overrides shorten by dropping `_id`/`_code` suffixes
(`..._collection_language`) or by naming the group of columns (`..._orders_statuses_updated_at`).

The framework's own answer — truncate and append an md5 hash — is deliberately **not** used: a
hashed name is unusable as something a developer later hand-writes in a `drop_index()` call, which
is the entire point of owning the names. Note 2.1.15 had no truncation at all, which is further
evidence no existing unnamed key overflows: such a table would have failed to create on alpha.1.

### 4. `Create*` migrations are left untouched

The new migration is the single place naming is decided. This keeps the diff to one new file rather
than 132 edits spread over 38 files, where a transcription slip would be easy to miss in review.

Accepted cost: the `Create*` files do not reflect the real names, and every fresh install does
redundant create-then-rename work forever. This is only safe **because** of Decision 6 — without
the inventory test, leaving `Create*` unnamed would let new drift in unnoticed.

### 5. Ordering is load-bearing

The migration registers in `config/migrations.php` immediately after the last `Create*` and before
the first `Alter*`. At that point an alpha.1 database is in post-`Create` state and a fresh install
has just finished its creates — **both populations are in the same state**, which is what lets one
code path serve both with no branching. The existing working-tree reordering that groups all
`Alter*` at the end is kept because the migration depends on it. The invariant goes in a file-level
comment: never reorder, never edit.

### 6. The guardrail is an inventory assertion, not a source lint

A test migrates a database from empty and asserts every key's name equals the name the scheme
produces for its table and columns. An unnamed key added by any future migration lands on a
framework-convention name, which by construction never equals a `*_kirki_*` scheme name — so it
fails immediately and names the offender.

*Alternative considered: parse migration source for unnamed `index()`/`unique()`/`foreign()` calls.*
Rejected — impossible once Decision 4 leaves `Create*` unnamed, and it would need a maintained
exemption list. The inventory assertion needs neither and is strictly stronger.

### 7. Ordering is schema-wide, not per table

InnoDB retains the backing index when a foreign key is dropped, and refuses to drop an index any
existing foreign key depends on. Crucially, *any* foreign key — not just one on the same table. The
unique index on `languages.code` is what makes the foreign keys on the three `*_translations`
tables legal, so it cannot be dropped while they exist, and they are not reachable from a pass over
`languages` alone. A per-table drop order is therefore unsound, and no amount of local reasoning
about one table can fix it.

The migration runs four schema-wide phases instead: drop **every** foreign key in the schema → drop
the indexes that need renaming, plus any backing index no longer carrying its constraint's name →
add the renamed indexes → restore every foreign key from its captured definition. Correctly named
constraints are dropped and restored along with the rest, because there is no way to ask the
database which index a given constraint depends on, so the only way to guarantee an index is free
is for no foreign key to exist at that moment. A plan is built up front and the whole schema is
checked for staleness before anything is dropped, which is what keeps the migration a no-op on a
database that has already been through it.

The whole run is wrapped in the framework's existing foreign-key-check suspension pair with a
`finally`, matching what `Migrator::rollback()` already does. That suspension is *not* what makes
the index drops legal — see the Risks section.

`down()` is a deliberate no-op. Restoring engine-assigned names is neither possible nor wanted.

### 8. Ground truth came from the 2.1.15 source, and the fixture is derived from it

The original plan called for resurrecting an alpha.1 install to observe its schema, because nothing
had been verified about what 2.1.15 emitted. That has now been settled more directly and more
reliably by reading 2.1.15's compiler at the pinned commit: the sole DDL difference affecting key
names is the absent `CONSTRAINT` clause on foreign keys.

The test fixture is therefore built by taking the current schema and stripping the `CONSTRAINT`
names from its foreign-key definitions, letting the database engine assign `_ibfk_n` itself exactly
as it did on alpha.1. This is faithful by construction and does not depend on resurrecting the old
build. Its accuracy rests on one verified claim — that the `CONSTRAINT` clause is the only
name-affecting difference — which is recorded in the fixture's header comment alongside the commit
it was verified against.

## Risks / Trade-offs

- **MySQL DDL is not transactional; a mid-run failure leaves a half-renamed database.** → The
  migration skips already-correct keys, so re-running completes the work rather than redoing it,
  and `Migrator::run()` only records a migration after `up()` returns cleanly, so a throw retries
  on the next load.
- **Swallowing per-table errors would hide a half-renamed database and break the `Alter*`
  migrations behind it in a far harder-to-diagnose way.** → The migration throws loudly.
  `version-updates.php` calls `migrator()->run()` in `before_each`, so a persistent failure
  surfaces repeatedly; that is the intended signal, not a bug.
- **Unique constraints are briefly absent between drop and re-add.** → Migrations run inside a
  single request, so exposure is small, but it is real under concurrent writes. Accepted at
  alpha-scale traffic.
- **Foreign keys owned by other plugins could be caught up in the sweep.** → Introspection filters
  on the child table being a `kirki_ecommerce_*` table, not merely on the referenced table. The
  converse is not defended against: a foreign key another plugin declares *against* one of our
  tables would block the drop of the index it references, because that constraint is not ours to
  remove.
- **`FOREIGN_KEY_CHECKS = 0` does not mean DDL is unconstrained, and the two engines disagree about
  how much it permits.** Measured directly: MariaDB 12.2 allows dropping an index required by a
  foreign key while checks are off; MySQL 8.0.46 refuses with `ERROR 1553`. Docker runs
  `mariadb:latest` while Local WP ships MySQL 8, so the permissive engine is the one under test and
  the strict one is what customers run. → The design must not depend on the suspension for
  legality at all, only for skipping row validation on re-add. Ordering is what makes the drops
  legal, and the ordering itself is asserted by a test (below) rather than inferred from a passing
  run.
- **Renaming indexes and uniques carries risk with no correctness benefit** — they already match on
  both populations, so ~75 of the 142 drops-and-recreates are purely for naming uniformity. →
  Accepted deliberately after the finding was raised: leaving four naming styles in place preserves
  the exact ambiguity that made this bug possible, and a scheme the guardrail can check for *every*
  key is stronger than one it can only check for foreign keys.

## Migration Plan

1. Produce and commit the legacy schema fixture (see Decision 8). No longer a gating unknown — the
   2.1.15 behaviour it reproduces has been verified from source.
2. Ship introspection, the migration, and its registration together; they are meaningless apart.
3. Verify convergence against the fixture in CI before release.
4. Run the full integration suite against **both** engines before release, not just the one Docker
   provides. MySQL 8.0.46 has been wired up and passes; the engines disagree about enough DDL that
   a MariaDB-only run is not evidence the upgrade works.
5. Manually run the upgrade against a restored copy of a real alpha.1 database, and once with the
   database image pinned to MariaDB 10.4 to confirm nothing depends on `RENAME INDEX` or
   `IF EXISTS`.

**Rollback:** none at the database level — `down()` is a no-op by design. Rollback is by not
shipping. Once released, a site that has run the migration stays on the explicit names, which is a
strictly better state regardless of what the plugin does next.
