## Context

See proposal.md — Why. Four facts constrain the approach. All four were
established by running the tooling, not by reading it.

- **`php-scoper --force` deletes the output directory before reading the
  source.** Pointing `--output-dir` at the package's own `src/` while the
  finder reads that same path destroys `src/` and then fails with *"The ...
  directory does not exist"*. In-place scoping is therefore never a one-step
  operation — it requires scope-to-staging, then swap.

- **The package's autoload map lives in `vendor/composer/installed.json`, and
  rewriting it works.** After install, `autoload_psr4.php` contains
  `'Framework\\' => <package dir>/src`. Patching the package's
  `psr-4` key in `installed.json` to `Kirki\Ecommerce\Framework\` and running
  `composer dump-autoload` removes the bare `Framework\` entry entirely. This
  is what `rm -rf vendor/themeum` currently achieves by deletion —
  `bin/make-package.sh:82` states as much: *"dumping the autoloader after the
  removal drops the stale `Framework\` psr-4 map."*

- **The package's own `files` autoload supplies the scoped helpers.**
  `installed.json` carries `files: [src/helpers.php, src/Polyfill/Polyfill.php]`,
  and `autoload_files.php` resolves them relative to the package's
  `install-path`.
  Once the package is scoped in place, those entries load the *scoped* helpers.
  This dissolves the chicken-and-egg `scoper.bootstrap.php` exists to solve:
  the files it stubs are real from the moment Composer finishes installing.
  **But they cannot be relied on for loading** — see Decision 2a; the ordering
  is wrong, so the package's `files` entry is stripped and the root package
  declares the same two files itself.

- **The scope step is not idempotent, and in-place scoping makes that
  reachable.** Re-running it over already-scoped code double-prefixes docblock
  annotations in 27 files —
  `@var \Kirki\Ecommerce\Kirki\Ecommerce\Framework\Database\Query\QueryBuilder`.
  Namespace declarations survive (`exclude-namespaces`'
  `/^(?!Framework($|\\))/` correctly skips already-prefixed namespaces); the
  culprit is the docblock patcher at `scoper.config.php:24`, whose pattern
  matches `\Framework\` *inside* `\Kirki\Ecommerce\Framework\`. **This bug
  exists today** — it is simply unreachable while the output is a throwaway
  directory rebuilt from pristine source on every run.

## Goals / Non-Goals

**Goals:**

- The code the plugin runs is the package Composer installed, prefixed in
  place — one copy, at the path `composer.lock` says it lives at.
- The shipped plugin registers no autoload mapping for the unprefixed
  `Framework\` namespace.
- `composer scope` is safe to run any number of times, in any order.
- The shipped zip is no larger than it is today.

**Non-Goals:**

- Renaming the Composer package, changing its version constraint, or touching
  the upstream `themeum/framework` repository.
- Changing the scoping prefix, the finder's `src` root, or the
  `exclude-namespaces` rules.
- Fixing the pre-existing `composer install --no-dev` gap (see Risks).

## Decisions

### Decision 1: Scope to a staging directory, then swap

`composer scope` becomes: scope the relocated package's `src/` into a
temporary directory, delete the original `src/`, move the staged output into
its place. Forced by the `--force` behaviour above.

The swap must be ordered `scope → verify → delete → move`, never
`delete → scope`. A failure during scoping then leaves the installed package
untouched rather than leaving no framework at all.

*Alternative considered — patch php-scoper's invocation to write in place.*
Not available; php-scoper has no in-place mode.

### Decision 2: Rewrite the package's `psr-4` prefix in `installed.json`

After the swap, rewrite the `themeum/framework` entry's `autoload.psr-4` key
from `Framework\` to `Kirki\Ecommerce\Framework\`, then `composer dump-autoload`.
Verified to remove the bare `Framework\` mapping.

The root `composer.json` **also** keeps an explicit
`"Kirki\\Ecommerce\\Framework\\": "vendor/libraries/framework/src/"` entry. This
is deliberate redundancy: `installed.json` is regenerated by every
`composer install`, so the patch is transient. The root map is the durable
one and guarantees the namespace always resolves; the `installed.json` rewrite
exists solely to remove the collision hazard. Losing the patch degrades to
today's status quo rather than to a fatal.

*Alternative considered — root-level override only, leaving the `Framework\`
map dead in place.* Rejected: a dead map that resolves to real files is worse
than no map. It shadows another plugin's genuine `Framework\` classes, and
the file it includes has side effects before the class-not-found surfaces.

*Alternative considered — patch the vendored package's own `composer.json`.*
Does not work: `composer dump-autoload` reads `installed.json`, not each
package's manifest.

### Decision 3a: Re-scoping converges rather than being byte-identical

Established while implementing Decision 3. With the patcher fixed, a second
pass over already-scoped code produces no double prefixes, but it does expand
same-namespace short references to fully-qualified ones —
`Arr::from(...)` becomes `\Kirki\Ecommerce\Framework\Supports\Arr::from(...)`,
and a bare parameter type `Request $request` becomes its FQN. This is
semantically identical: both forms resolve to the same class from inside the
already-prefixed namespace.

A third pass is byte-identical to the second, so the transform reaches a fixed
point after one re-scope and stays there. Practically: `composer scope` is
safe to run any number of times, but the source text of a package scoped once
differs cosmetically from one scoped twice or more. Nothing downstream depends
on which form is present.

### Decision 3: Fix the docblock patcher rather than guard against re-running

Add a negative lookbehind so the patcher skips `\Framework\` already preceded
by the prefix. This makes the whole scope step idempotent, which is a
precondition for in-place scoping being safe at all.

*Alternative considered — reinstall the package before every scope run.*
Robust, but it makes every scope run re-copy the package and adds a dependency
on `composer reinstall`. It also treats the symptom: the patcher would still
be wrong.

*Alternative considered — skip if already scoped.* Rejected: a partially
scoped directory from an interrupted run reads as complete, and is then
silently left broken.

Fixing the regex is also the only option that repairs the latent bug for the
current design, independent of this move.

### Decision 2a: The package's `files` autoload must be removed, not reused

Discovered during implementation, and it corrects an assumption in Context
above. Composer emits dependency `files` entries **before** the root package's.
The framework's `helpers.php` opens with `defined('ABSPATH') || exit;`, so
relying on the package's own `files` autoload put it at position 111 of
`autoload_files.php` while `bootstrap/abspath.php` — which defines ABSPATH —
sat at 114. Every CLI process that required `vendor/autoload.php` therefore
`exit`ed silently with status 0. PHPUnit produced no output at all.

This is invisible under WordPress, which defines ABSPATH long before plugins
load, and it is easy to mask in a smoke test by defining ABSPATH before the
require.

So `bin/scope-framework.php` strips `autoload.files` from the package's
`installed.json` entry alongside the `psr-4` rewrite, and the root
`composer.json` lists the same two files itself, positioned after
`bootstrap/abspath.php`. The ordering then matches what the old
`libraries/framework` layout produced.

The stub-creation logic in `scoper.bootstrap.php` still goes away: the root
`files` entries now point at `vendor/libraries/framework/src/...`, which exists
from the moment the relocation step runs — and that step runs before anything
loads the autoloader (Decision 6) — so there is nothing to fabricate.

### Decision 6: Relocate the installed package rather than teach Composer to install it there

The plugin runs the framework from `vendor/libraries/framework`, but Composer
installs it at `vendor/themeum/framework` — the path is derived from the
package name and there is no way to change it without a Composer installer
plugin. `composer scope` therefore moves the directory after install and
repoints `install-path` in `vendor/composer/installed.json` to
`../libraries/framework`.

**The relocation must run before anything loads `vendor/autoload.php`.**
Established by running it the other way round first: a fresh `composer install`
dumps an autoloader whose *dependency* `files` entry resolves through the
package's `install-path`, and php-scoper's own bin requires that autoloader —
so scoping died with `require(vendor/composer/../themeum/framework/src/helpers.php):
Failed to open stream`. `scripts.scope` is consequently ordered:
`--relocate` (move + metadata rewrite) → `composer dump-autoload` → php-scoper
→ finish → `composer dump-autoload`. The `--relocate` step is plain PHP and
loads no autoloader itself, so it is safe to run in that window.

**Composer re-clones the package on every install, and `install-path` does not
stop it.** Also established empirically, by inspecting a built zip. Composer
decides whether a package is installed by testing the path it *derives from the
package name* — `vendor/themeum/framework` — not the `install-path` recorded in
`installed.json`. A relocated package therefore reads as missing and is
reinstalled. Its autoload generator behaves the same way: it contributes
`vendor/themeum/framework/src` to the PSR-4 map whenever that directory exists,
and silently contributes nothing when it does not.

Two consequences follow.

- **The load-bearing invariant is the absence of `vendor/themeum`,** not the
  `install-path` value. `--relocate` removes the parent directory once empty
  for exactly this reason. The `install-path` rewrite is kept only so
  `installed.json` does not misstate where the package physically lives;
  nothing in the autoload pipeline reads it.
- **With scripts enabled this is self-healing** — `post-install-cmd` /
  `post-update-cmd` relocate the fresh copy and re-scope it, which is the
  correct response to a version bump. With `--no-scripts` it is not, and
  `bin/make-package.sh` runs exactly that. Its first build after the move
  shipped a complete *second*, unscoped framework — tests, docs, `.github` and
  all — registered in the autoloader alongside the scoped one. The `--restore`
  mode exists to undo it: remove the reinstalled copy, re-apply the metadata.
  `--restore` refuses to delete anything unless the scoped copy is verifiably
  present, so it cannot leave a build with no framework at all.

The relocate step is idempotent, and handles the both-directories-exist case
(Composer has reinstalled since the last scope) by discarding the stale scoped
copy before moving the fresh one.

*Alternative considered — restore the old `rm -rf vendor/themeum` in
`bin/make-package.sh` directly.* Functionally the same delete, but an
unguarded one: a bare `rm -rf` after a failed scope run removes the only copy
of the framework and the build ships without it. Putting it behind `--restore`
keeps the guard and the vendor-layout knowledge in one file.

*Alternative considered — `composer/installers` + `oomphinc/composer-installers-extender`
to make Composer install to `vendor/libraries/framework` natively.* Correct in
principle, and it would remove the relocation entirely. Rejected on packaging
grounds: the plugin type is `library`, so mapping an arbitrary path needs the
extender, and both plugins would have to sit in `require` (not `require-dev`)
for `bin/make-package.sh`'s `--no-dev` install to honour the path. That ships
two Composer plugins inside a wp.org plugin zip to avoid one `rename()`.

*Alternative considered — leave the package at `vendor/themeum/framework`.*
That is what the first implementation of this change did. Superseded by an
explicit requirement that third-party scoped code sit under a neutral
`vendor/libraries/` path.

### Decision 4: Strip non-runtime files from the package after scoping

Keep `src/`, `LICENSE`, and `composer.json`; remove `tests/`, `docs/`,
`example/`, `docker/`, `scripts/`, `stubs/`, `phpcs/`, `Makefile`,
`docker-compose.yml`, `phpunit.xml`, `phpstan.neon.dist`, `phpcs.xml.dist`,
`composer.lock`, and the framework's own `README.md`/`CLAUDE.md`.

`LICENSE` stays because the plugin redistributes the dependency. `composer.json`
stays because Composer reads it when regenerating metadata.

Stripping happens in the scope step rather than only in `bin/make-package.sh`,
so development and shipped states match — a build-only strip means the thing
being packaged has never been tested in the shape it ships in.

### Decision 5: Put the relocate, swap, rewrite, and strip in a script under `bin/`

Steps involving two directory moves, a JSON edit, and a selective delete do not
belong inline in `composer.json`'s `scripts` array. `scripts.scope` invokes the
script's `--relocate` mode, dumps the autoloader, runs php-scoper, then invokes
the script again to finish; `remove-framework-from-vendor` is deleted.

## Risks / Trade-offs

- **[The swap can leave the package half-replaced]** → An interruption between
  deleting `src/` and moving the staged copy leaves no framework at all, and
  `composer install` will not repair it (Composer compares `installed.json`
  against the lock, not file contents). → Mitigation: order the steps so
  scoping fully succeeds before anything is deleted, and document
  `rm -rf vendor/themeum vendor/libraries && composer install` as the one-line
  recovery.

- **[`bin/make-package.sh` discards the `installed.json` rewrite]** → Its
  `composer install --no-dev --no-scripts` regenerates `installed.json` from
  the lock, restoring both the bare `Framework\` map and the
  `../themeum/framework` install path, and its subsequent
  `dump-autoload --no-dev --optimize` bakes those into the shipped autoloader.
  The stale map would then ship despite Decision 2, pointing at a directory
  the package no longer occupies. → Mitigation: `--metadata-only` re-applies
  both after the final install, before the final `dump-autoload`. Verified by
  inspecting the built zip's autoload maps, not by reasoning about script
  order.

- **[Scoped code now lives in a Composer-managed directory]** → A framework
  version bump reinstalls unscoped source over the scoped copy. This is
  correct and expected — `post-install-cmd`/`post-update-cmd` re-scope
  immediately after. It is only a hazard when scripts are skipped. →
  Mitigation: Decision 3 makes re-scoping harmless, so the recovery is always
  "run `composer scope`".

- **[`composer install --no-scripts` yields a silently broken plugin]** →
  Unscoped source with the root map expecting prefixed classes. → Same failure
  class as today (where it yields a missing `libraries/`), and the same fix.
  Documented, not engineered around.

- **[Pre-existing, unchanged: `composer install --no-dev` skips scoping]** →
  The `post-install-cmd` hook checks `argv` for `--no-dev` and does not scope.
  `bin/make-package.sh` already works around this by running a full install
  first. Out of scope; noted so it is not mistaken for a regression.

- **[`vendor/` no longer matches a pristine Composer install]** → `src/` is
  rewritten and dev files are deleted, so the tree diverges from what the lock
  would produce. Composer will not notice or repair it. Accepted: this is the
  explicit intent, and it is what `libraries/framework` already represents
  today — the divergence merely becomes visible in `vendor/`.

## Migration Plan

1. Fix the docblock patcher first, in isolation, and confirm a second scope
   pass over scoped output is a no-op. Everything downstream depends on this.
2. Add the `bin/` script (relocate, swap, `installed.json` rewrite, strip) and
   rewire `scripts.scope`; delete `remove-framework-from-vendor`.
3. Repoint the autoloader, phpunit, phpcs, `.gitignore`, and docs; simplify
   `scoper.bootstrap.php`.
4. Delete `libraries/`, run a clean `composer install`, and verify the
   generated autoload maps directly.
5. Run the test suite and `composer phpcs:wporg`.
6. Run `bin/make-package.sh` and check the built zip against the
   `plugin-packaging` spec delta — including that no bare `Framework\` map
   survives its `--no-dev` install.

**Rollback**: revert the commit, then
`rm -rf vendor/themeum vendor/libraries && composer install`.
The old pipeline regenerates `libraries/framework` and deletes
`vendor/themeum`. No committed source, data, or schema is involved.
