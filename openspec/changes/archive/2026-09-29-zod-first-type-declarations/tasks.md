- [x] 6.5 Added `ApiEnvelopeSchema` (`schemas/shared/api.ts`) and used it in `parseData`/`parseResponse` to validate `{ data }` exists before touching `.data`, so a malformed non-object response reports a clean `ApiValidationError` instead of a raw property-access crash. Correcting the rest of the task's premise: `parseData`/`parseResponse` were already correctly *not* unified — queries have no `onError` in React Query v5, so `parseData` must toast directly to reach the user; mutations still have `onError`, so `parseResponse`/`parseMessage` only throw, letting the mutation's `onError` (or, for product, the page-level catch) report it once. Did **not** add `onError` to the product create/update mutations: `product-form.tsx`'s `handleSave` already wraps `mutateAsync` in its own try/catch calling `applyServerErrors` + `toast.error(getErrorMessage(error))` — richer than a generic `onError` since it can focus the failing field, and adding a mutation-level `onError` alongside it would double the toast for every product save failure. Verified product's two mutations have no other call site that would bypass this handling

- [x] 6.9 Smoke-tested via the live app (docker WordPress backend + Vite dev server) with the browser tools. Email-template `logo`: selected a real media library image, saved, confirmed the PUT body round-tripped with no dev tripwire warnings. Product `media[]`/`og_image`: created a real product with a media-library image — this caught a genuine pre-existing bug, not something I introduced: `schemas/shared/media.ts`'s `MediaRefSchema.date` was typed `z.string().optional()`, but WordPress's real attachment objects send `date` as either a JS `Date` instance (from the media picker's `attachment.toJSON()`) or a raw millisecond timestamp number (from the `query-attachments` AJAX response) — never a string.
