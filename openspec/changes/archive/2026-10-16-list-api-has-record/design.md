# Design

## Context

Nine services return `->paginate(...)` straight from the query builder. The result is the framework
`Paginator` (`vendor/libraries/framework`, scoped and regenerated by `composer scope`, so it cannot be
edited). `Resource::paginated()` calls `$paginator->to_array()` and maps `results` through the resource.
Any extra key in `to_array()` therefore reaches the response with no resource or controller change.

The framework `Paginator` keeps its state in `protected` properties and exposes `items()`, `total()`,
`get_per_page()` and `get_current_page()`, so a subclass in `app/` can be built from a finished paginator.

The nine pages each compute `hasRecord` as `!(!isFetching && !hasActiveFilters && data?.total === 0)` with an
`@todo` to use the server value. `PaginatedData` in `types/api/response.ts` and `PaginatedDataSchema` in
`schemas/shared/api.ts` already declare an optional `has_records` (plural). Nothing reads it.

Controllers have a second branch for `limit === Pagination::ALL`. It builds a bare `Paginator` from
`all()`. That branch is for pickers and exports, not for list pages.

See proposal.md for motivation and `specs/list-record-presence` for requirements.

## Goals / Non-Goals

**Goals:**

- One place defines the `has_records` key and its cost rule.
- A service opts in with one line and can change the presence rule with its own query.
- No change to resources, controllers or the existing keys.

**Non-Goals:**

- The `limit=ALL` branch, storefront lists (wishlist, account orders view), and settings lists.
- Changing how `DataTable` decides its own first-use row. Pages stop rendering the table when the server
  says the table is empty. The inner logic is left as is.

## Decisions

### D1. Subclass `Paginator` in `app/Supports/ListPaginator.php`

`ListPaginator extends Paginator`. It adds a `has_records` property, a static `from()` and a `to_array()`
that returns the parent array plus `has_records`.

- **Why:** `Resource::paginated()` already calls `to_array()`, so nothing else changes. The service return
  type stays `Paginator` (a child class), so no caller breaks.
- **Alternative:** a trait on models. Rejected: the rule depends on the screen, not on the model.
- **Alternative:** add the key in `Resource::paginated()`. Rejected: the resource has no query and the
  framework class cannot be edited. An app base resource would run database queries in a formatter.
- **Alternative:** the controller adds the key. Rejected: nine controllers repeat it, and the `ALL` branch
  makes it easy to forget one.

### D2. `from( Paginator $paginator, bool|QueryBuilder $has_records )`

The second argument is either a ready `bool`, or a query. A query is run with `exists()` and only when
`$paginator->total() === 0`. When `total() > 0` the value is `true` with no lookup.

- **Why:** one rule, held in one place. A service never repeats the `total() > 0` shortcut.
- **Why `total()` and not `count()`:** `total()` is the filtered total over all pages. A page past the last
  page has `count() === 0` but `total() > 0`, and the answer is still "has records".
- **Alternative:** accept a `Closure`. Rejected: nothing needs it yet. A `bool` already covers a caller that
  has the answer, and a query covers the rest.

### D3. The query must be fresh and unfiltered

Each service passes a new query such as `Brand::query()`, never the filtered list query. A filtered query
would turn "has any record" into "has a match", and a search with no results would show the first-use state.

- **Note:** a list query is a mutable builder and `paginate()` has already applied filters to it. Reuse is
  wrong even if it looks cheaper.
- **Order exception:** the order service also serves the storefront account list through the same method,
  scoped by `customer_id`. The query it passes carries that one scope, so the flag is "this customer has
  orders" there and "the store has orders" for admin.

### D4. Default rule is the plain model query; products ignore trashed

Collections, categories, tags, brands, customers, coupons, variants and orders pass `Model::query()`.
Products pass `Product::query()->where_not('status', ProductStatus::TRASHED)`, the same rule the product
list applies by default.

- **Why:** a store that holds only trashed products should see "add your first product", like an empty store.
- **Note:** the trash view stays reachable through the product list's status filter once the page shows the
  table, but a store with only trashed products shows the first-use state and no filter. Accepted by the user.

### D5. Name the key `has_records`

The key is plural, matching the unused `has_records` field that `PaginatedData` and `PaginatedDataSchema`
already declare. The Zod object drops keys it does not list, so any other name would never reach a page.

- **Alternative:** `has_records` (singular), as in the page `@todo` comments. Rejected: needs a type and
  schema rename for no gain. The `@todo` comments are removed in this change.

### D6. Page logic: show the empty state only on an explicit `false`

```
hasRecord = data?.has_records !== false
```

`undefined` (loading, error, no data) keeps the table path, so a failed request is never shown as
"add your first item". This also removes the dependency on `hasActiveFilters` and `isFetching` in the
empty-state decision. `hasActiveFilters` stays in use inside `DataTable` for its own filtered-empty message.

- **Alternative:** keep the old derived guess and use `has_records` only as a tiebreaker. Rejected: two
  sources of truth for one decision.

## Risks / Trade-offs

- **[Risk] A service forgets to wrap its result** → the key is absent, `data.has_records` is `undefined`,
  and the page shows the table, never a false empty state. The failure is safe. Each service gets a test.
- **[Risk] A future caller passes the filtered query** → wrong flag. → The `from()` docblock states the rule,
  and the nine call sites show the pattern.
- **[Risk] Extra `exists()` query on an empty list** → one cheap query, only when `total` is 0.
- **[Trade-off] A pure subclass cannot change what the base class stores** → `ListPaginator::from()` copies
  the four constructor inputs from getters. If the framework adds a property later, `from()` must copy it too.
- **[Trade-off] Products with only trashed rows** → `has_records: false`, the page shows the first-use state
  and the trash cannot be reached from it until a product is created.

## Migration Plan

No data or schema change. Ship backend and frontend together. If the frontend ships first, `has_records` is
`undefined`, pages show the table, and the first-use state is lost until the backend lands. If the backend
ships first, the new key is ignored. No rollback step beyond a normal revert.
