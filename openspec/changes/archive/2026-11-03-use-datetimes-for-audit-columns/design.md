# Design

## Context

See proposal.md, "Why". Facts found in the code:

- `Structure::datetimes()` exists in the framework (`vendor/libraries/framework/src/Database/Schema/Structure.php`). It makes `created_at` with `datetime(...)->use_current()` and `updated_at` with `datetime(...)->nullable()`. `timestamps()` makes the same two columns with `timestamp(...)`. The signature is the same (`$precision = 0`), so no call passes an argument that needs a change.
- 43 files call `$table->timestamps();` with no argument: 41 in `database/migrations/` and 2 in `app/Migration/Database/Migrations/`. No other `->timestamp(` call remains in `app/` or `database/`.
- Model writes set `created_at` and `updated_at` in PHP as UTC strings. The four bulk-insert sites already pass UTC strings (change `datetime-utc-columns`). So the database default runs only for raw inserts that skip both.
- `UtcDateTimeStorageTest::test_no_named_date_column_is_a_timestamp` excludes `created_at` and `updated_at` and says to remove the exclusion when the framework creates `DATETIME`.
- `vendor/libraries/framework/` is generated by `composer scope`. It must not be edited by hand.

## Goals / Non-Goals

**Goals:**
- After a fresh install, no column of any plugin table has the type `timestamp`.
- The guard test fails if a `timestamp` column returns.

**Non-Goals:**
- An upgrade path for existing alpha installs. The reinstall policy applies.
- A change to the framework. `datetimes()` already exists.
- Removing `timestamps()` from the framework, or a lint rule that forbids it.
- Sub-second precision. Columns stay at precision 0.

## Decisions

### D1. Edit the `Create*` files; write no alter migration

Same reason as `datetime-utc-columns` and `money-columns-bigint`: the squash change set the reinstall policy, and an alter migration would restart a chain that was just deleted.

### D2. Change the call in place, one line per file

Replace `$table->timestamps();` with `$table->datetimes();` and touch nothing else. Do not change column order: `datetimes()` adds the same two columns at the same position.

- **Alternative: two explicit `datetime()` lines per file.** Rejected: `datetimes()` does exactly this and is the framework's own call.

### D3. Remove the guard exclusion in the same change

The test then covers every column. No column list needs to be kept.

## Risks / Trade-offs

- **[The `use_current()` default on `DATETIME` needs MySQL 5.6.5 or MariaDB 10.0]** → The test database (MariaDB 12.3) accepts it. WordPress 6.x already requires MySQL 5.5.5+ or MariaDB 10.0+. Confirm the plugin's minimum DB version in the apply step.
- **[Existing alpha installs keep `TIMESTAMP` columns]** → Accepted by the reinstall policy. The next alpha release notes should say it.
- **[A raw insert skips `created_at` and relies on the database default]** → The default is `CURRENT_TIMESTAMP`, which follows the session time zone. Same risk as before this change. Model writes and the four bulk-insert sites already pass UTC.

## Migration Plan

1. Replace the call in the 43 files.
2. Remove the exclusion from the guard test.
3. Run the integration test on a fresh database, then all suites.
4. Reinstall the plugin on any alpha test site (deactivate, drop the plugin tables, activate).

Rollback is a revert of the commit, because no data migration runs.
