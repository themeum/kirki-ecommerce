- [x] 3.3 Rewrite `DiscountService::calculate()` to accept an array of coupons: validate each individually (existing `validate_coupon()` checks; a coupon that fails validation is recorded in `invalid_coupons` and excluded, not a fatal error for the others), then run pass 1 (item-scoped `amount-off` coupons, each capped at the item's own subtotal and summed when more than one applies to the same item) followed by pass 2 (order-scoped `amount-off` coupons, applied sequentially against the subtotal remaining after pass 1 and each previous pass-2 coupon). `free-shipping` coupons are recorded in `coupon_results` with `shipping_discount` left unset (the caller fills it in once the shipping total is known); `buy-x-get-y` coupons are recorded with a zero `total_discount` (matches today's no-op, keeps the record for later).
- [x] 3.4 Add the largest-remainder allocation helper for splitting one coupon's discount proportionally across items: truncate each item's integer-minor-unit share, then distribute the leftover minor units to the items with the largest truncated remainder until none is left.

- [x] 3.6 Update `DiscountService::validate_conditions()`'s customer-limit check to query `Coupon::order_coupons()` (via `customer_id`) instead of `Coupon::usage()`.

## Frontend Follow-Up (out of scope for this change — guide only, no tasks below are implemented here)

The backend/API work above ships with `pricing.coupons` (cart) and `coupons` (order) as arrays. The following surfaces still assume a single coupon and will break or silently show only one coupon until a separate follow-up change updates them:

- **Admin order-create** — `resources/app/features/orders/components/order-create/payment/discount-popover.tsx` and `payment-summary-card.tsx` apply/display one coupon; need to become a list (apply another, remove one of several).
- **Admin order details** — `resources/app/features/orders/pages/order-details.tsx` reads a single legacy coupon field; needs to render the order's `coupons` array, and ideally show per-item attribution and whether a coupon's usage was reversed (cancelled order).
- **Admin types/schemas** — `resources/app/features/orders/schemas/catalog/order.ts` and `resources/app/features/coupons/types.ts` model the old singular discount shape and need updating to match the new array response.
- **Storefront cart API client** — `resources/site/ts/api/cart.ts`: `removeCoupon()` takes no argument today; needs a coupon code/id parameter.
- **Storefront checkout state** — `resources/site/ts/components/checkout.ts` tracks a single `appliedCouponCode`; needs to become a list (`appliedCoupons`), with `removeCoupon` passing the specific coupon's identifier.
- **Storefront coupon UI** — `resources/views/site/checkout/parts/coupon-form.php` reads `cartData.pricing.discount_details` for a single applied coupon; needs to iterate `cartData.pricing.coupons` and give each an independent remove control.
- **Coupon request field rename** — every client call to the order-calculation, order-create, and order-update endpoints must send `coupon_codes: string[]` instead of `coupon_code: string`; the backend fallback that accepted the old singular field is removed in task 8.5/8.6. Until the frontend switches, those endpoints will silently stop picking up an applied coupon. (The `apply_coupon`/`remove_coupon` cart endpoints are unaffected — they keep taking one `code` at a time.)

None of the above is implemented as part of this change; hand this list to whoever picks up the frontend follow-up.
