## Context

See `proposal.md` — Why. The constraints that actually shape this design:

- **The framework `Seeder` base class is minimal.** `libraries/framework/Database/Seeder.php`
  exposes only `call()` (enqueue), `run()` (override), and `__invoke()` (drain the
  queue). `call()` does *not* execute — a grouping seeder needs `->run()` then `()`.
  The `$called`/`$resolved` queues are static and process-scoped, so they give no
  cross-request idempotency.
- **`libraries/framework/` is vendored** — regenerated by `composer scope`. It cannot
  be hand-edited, which rules out fixing `SeedCommand::discover()`'s non-recursive
  `glob()` or its dead `--class` flag.
- **The version-update callback is not transactional and not atomic.**
  `VersionUpdateManager::run()` records the version *after* the callback returns, on
  `admin_init`. A timeout or fatal mid-seed re-fires the whole callback — including
  the `migrator()->run()` already in it — on the next admin request.
- **`AppSettings::refresh()` shallow-merges** `resources/data/settings/<key>.json`
  under the stored option. Writing a top-level key replaces the default's version of
  that key wholesale; nested keys are not deep-merged.
- **The root `.md` source files are not shipped.** `bin/make-package.sh` copies an
  explicit path list that excludes root-level markdown, so `categories.md`,
  `colors.md`, and `schema.md` do not exist at runtime.
- **No media-import machinery exists.** A repo-wide search finds zero uses of
  `wp_insert_attachment`, `wp_upload_bits`, `media_handle_sideload`, or
  `wp_generate_attachment_metadata`. Existing seeders reference attachment IDs
  (`'media' => [1,2,3]`) that are simply assumed to exist.

## Goals / Non-Goals

**Goals:**

- Survive the re-fire hazard above without a transaction, since media files written
  to `uploads/` cannot be rolled back and a PHP timeout never reaches a rollback.
- Keep the onboarding data completely disjoint from the demo seeders, which are
  mutually incompatible with it (hardcoded IDs, unconditional inserts,
  settings-clobbering).
- Never lose merchant configuration, on any run.

**Non-Goals:**

- Re-runnability as a feature. There is no CLI command and no `--force`. Re-seeding
  from scratch in development is a manual table truncate.
- Correcting the vendored `SeedCommand`'s discovery and `--class` bugs. Documented
  here, fixed elsewhere.
- Extending the product-form schema picker to cover the extra JSON-LD fields in
  `schema.md`. Deferred until a JSON-LD renderer exists — today nothing reads the
  `schema` column except the picker.

## Decisions

### Guard per concern, not per run

Each child seeder tests its own target (`Currency` where `code = 'usd'`, any
`Category` row, `Attribute` by slug, any `ProductSchema` row, per-key option
presence, any `Product` row) and returns early when satisfied.

*Alternative rejected — a single `onboarding_completed` option flag:* a mid-seed
fatal leaves partial data *and* no flag, so the retry duplicates everything already
written. Per-concern guards make the retry resume instead of repeat.

*Alternative rejected — `DB::begin_transaction()` around everything* (as
`SeedCommand::seed()` does): attachment *files* land in `uploads/` outside the
transaction and would be orphaned by a rollback, and a PHP timeout kills the process
before any rollback runs.

Attribute guards are per-attribute rather than per-seeder, so a run that created
`Color` but died before `Material` completes correctly on retry.

### No hardcoded primary keys

Every existing demo seeder writes explicit `id` values, which is why they fatal on a
second run and why they cannot coexist with merchant data. Categories are inserted
level-by-level with the parent level's real inserted IDs collected in between;
attribute values and categories are resolved by slug when products are built.

### Category slugs: parent-prefix only on collision

`kirki_ecommerce_categories.slug` is UNIQUE and the tree has 14 colliding leaf names
(`accessories` ×5, `shoes`/`helmets`/`toys` ×3, plus 10 more). Rule: `Str::slug($name)`,
falling back to `Str::slug($parent . '-' . $name)` when taken.

*Alternative rejected — prefix every child:* 221 categories that never collide would
get needlessly long storefront URLs. *Alternative rejected — `HasSlug::generate_unique_slug()`:*
its numeric increment (`accessories-1`) is arbitrary and depends on insert order, so
slugs would not be stable across installs.

### Settings written by the seeder, per-key, only when absent

Settings go through `Option::set` rather than by editing the shipped JSON defaults,
keeping onboarding values in one place with the rest of the seed. Each key is written
only when its option row does not yet exist, which is what makes it safe against the
re-fire hazard and against a merchant who has already configured that group.

Each payload starts from the shipped `resources/data/settings/<key>.json` default and
applies overrides on top, so the seeder does not have to restate the full settings
tree and cannot drift from it.

Two live-key corrections the payload must respect:

- The offline payment methods key is **`offline_payments`**, not the `payment_gateways`
  key currently sitting in `resources/data/settings/payment.json` — that key is read by
  nothing. `OfflinePaymentFactory`, `OfflinePaymentService`, `SettingsUpdateRequest`,
  and the admin SPA all use `offline_payments`.
- Its per-method fields are **`name`** and **`instructions`**, not title/description.
  `PaymentProvider::from_offline()` maps `name → title` and `instructions → description`.
  `icon => null` satisfies "no icon"; `from_offline()` only resolves an icon when the
  value is an integer attachment ID, so a string there would resolve to null anyway.

### Media import is a plain collaborator, not a seeder

The importer is a small non-`Seeder` class used by the product seeder. Files are
local, so it uses `wp_upload_bits()` → `wp_insert_attachment()` →
`wp_generate_attachment_metadata()` → `wp_update_attachment_metadata()` rather than
`media_handle_sideload()`, which expects an upload-shaped temp file. It
`require_once`s `ABSPATH . 'wp-admin/includes/image.php'`, which is not guaranteed
loaded on `admin_init`.

Idempotency comes from stamping each attachment with a post meta key recording its
source filename and looking that up before importing — an image imported by an
earlier partial run is reused, not duplicated.

Import failure returns `null` rather than throwing: a store that cannot write to
`uploads/` should still get its catalog, just without imagery. The caller records
that a failure occurred so cleanup is suppressed.

### Image cleanup gated on `KIRKI_ECOMMERCE_MODE`

`docker-compose.yml:3` bind-mounts the repository itself as the plugin directory, so
an unconditional delete would remove the source `.webp` files from the developer's git
working tree. `bin/make-package.sh` patches `KIRKI_ECOMMERCE_MODE` from `development`
to `production` when building the zip, which is exactly the signal needed: images stay
in git and ship in the package, and only an installed production plugin reclaims the
directory. Cleanup is additionally suppressed unless every image imported, so a retry
can still find its sources.

### Static data baked into PHP

A single catalog class (mirroring `database/seeders/SeedCatalog.php`, which likewise
does not extend `Seeder`) holds the category tree, colour presets, schema profiles,
and product definitions as PHP literals. Runtime parsing of the root `.md` files is
impossible — they are not packaged.

Product prices are stored in **minor units**, matching `SeedCatalog` (`99900` = $999.00).

### Products built through `CreateProductAction`

The demo products go through the same action the REST API uses, so variant/attribute
wiring, `has_variants` derivation, and the media pivot ordering all behave exactly as
they would for a merchant-created product. The product-level `media` field is an array
of attachment IDs whose order becomes the pivot `ordering`; the variant-level `media`
field is a single integer.

The product without variants still gets one default variant, since price and inventory
live on the variant.

## Risks / Trade-offs

- **Callback re-fire mid-seed** (timeout during the 10-image import) → per-concern
  guards make the retry resume rather than duplicate. Note `migrator()->run()` in the
  same closure already carries this exposure today; this change does not add it.
- **`uploads/` not writable** → every import returns `null`, products seed without
  imagery, cleanup is suppressed, and the run still succeeds. Degraded, not broken.
- **255 categories on a first admin request** → inserted as three bulk statements
  (one per level), not 255 round-trips.
- **Deleting plugin files at runtime is unusual.** A plugin update restores the
  directory, and the version-update will not re-fire to re-delete it. Accepted: the
  cost is 396 KB of inert files.
- **Guarding on "any row exists" is coarse.** A merchant who deletes every category
  and then triggers a re-fire would get the tree back. Acceptable for a first-run
  dataset, and far safer than the alternative of duplicating into a populated store.
- **The onboarding seeders are unreachable from `wp kirki db:seed`.** This is
  deliberate (they must not run alongside the demo seeders), but it means the only way
  to exercise them in development is deleting the installed-version option and
  truncating tables. The vendored `SeedCommand` could not have been fixed anyway.

## Migration Plan

No database migration and no data backfill. The seed is additive and gated on the
`1.0.0-alpha.1` version key, which no existing install has recorded. Rollback is
dropping the seeded rows and the written option keys; there is no schema change to
reverse.
