Task groups follow the five stages in `design.md` — Migration Plan. Every group ends with `npm run typecheck && npm test` from `resources/app/`. Parse tests go next to the schema they cover (`<name>.test.ts`), and each one asserts three things: the exact documented 200 body from `docs/ecommerce/` parses, an unknown extra field is accepted and ignored, and the optional fields can all be absent.

## 5. Live verification

- [x] 5.1 Visited all eight settings routes against the real docker WordPress backend + Vite dev server (`admin.php?page=ecommerce#/settings/{general,products,checkout,email,shipping,tax,payments,currency}`). General, Products, Checkout, Email, Shipping, and Payments rendered clean on the first pass. **Two real, live-data-only validation failures were found and fixed** (not visible from the documented bodies used to write the schemas — this is exactly the risk the plan's "Risks" section named as the reason this task isn't optional): (1) Tax — `tax_regions.0.product_tax.0.state: Required`. Live data showed the EU region's `product_tax`/`shipping_tax` entries keyed by `country`, not `state` (`{"country":"AT","rate":20}`); the general (Bangladesh) region's entries do use `state`. Fixed by making both `state` and `country` optional on `TaxRateSchema` (`schemas/catalog/tax.ts`) — this also required widening the page-local `TaxRate` type in `pages/settings/tax-settings/utils.ts` (same fields, same reasoning) and a one-line fix in `vat-collection.tsx` (`getFlagForState(item?.state ?? '')`) to keep typecheck clean. (2) Currency — `api_config: Expected object, received array`. Live data sends `api_config: []` (PHP empty-array-as-object, the same pattern already handled on `PaymentGateway.config`) when no provider is configured. Fixed by widening `CurrencySettingsSchema.api_config` to `z.union([CurrencyApiConfigSchema, z.array(z.unknown())]).nullish()`. Both fixes verified live afterward (reloaded page, confirmed the error toast and console `ApiValidationError` were gone) and both pre-existing test suites still pass unchanged
- [x] 5.2 Confirmed — `/settings/payments` now renders (Manual payment methods: 2x Cash on Delivery; Payment gateways: PayPal, Inactive), with no console errors. It was unreachable before this change per `project.md`'s prior known-issue entry
- [x] 5.3 Shipping and Tax: confirmed by toggling a real switch (shipping zone enabled state; EU tax region enabled state) and clicking Save — both produced a `200 OK` PUT with a real settings payload in the response body and no `ApiValidationError`, then reverted both toggles back with a second save each. General: **not completed as originally scoped**. Saving general settings 422's at the PHP layer (`store_address.{address_line_1,city,state,postal_code,country}` are required by the backend once *any* general-settings field changes, and this store's address was entirely empty) — a pre-existing backend requirement unrelated to this change, confirmed by the error being a Laravel-style validation response naming required fields, not a schema/zod error. Filling in the address to get past it required driving a virtualized country-search combobox that the available browser-automation tools could not reliably click through (multiple attempts via ref-click, keyboard nav, and dispatched DOM events all left the popover in an inconsistent state); given Shipping and Tax already exercise the identical `updateSettings` → `parseResponse(SettingsSchemaMap[key], ...)` code path with two different section schemas, this was judged sufficient evidence for the task's actual purpose (confirm mutation responses parse) rather than continuing to fight the combobox
