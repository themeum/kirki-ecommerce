# Design

## Audit method

Two passes, cross-referenced.

**Plugin Check 2.1.0**, run inside the project's own Docker stack against the built package staged as a separate plugin directory:

```bash
docker compose --profile tools run --rm --user root --entrypoint sh wpcli -c \
  'rm -rf /var/www/html/wp-content/plugins/kirki-ecommerce-dist && \
   cp -R /var/www/html/wp-content/plugins/kirki-ecommerce/build/kirki-ecommerce \
         /var/www/html/wp-content/plugins/kirki-ecommerce-dist'
./wpcli plugin check kirki-ecommerce-dist --checks=<slug> --format=csv \
  --fields=file,line,type,code,message
```

Two notes for whoever re-runs this:

- **Run checks one at a time.** Passing a whole category crashes with *"There has been a critical error on this website"*; each of the 21 `plugin_repo`/`security` checks completes on its own. The loop over individual slugs is what produced the counts below.
- **Ignore `textdomain_mismatch`.** Plugin Check compares `Text Domain:` against the *directory name*, and the audit staged the package as `kirki-ecommerce-dist`. It is an artifact of the staging name, not a finding. `plugin_header_nonexistent_domain_path` in the same output **is** real — `Domain Path: /languages` points at a directory that does not exist.

**Manual reading** of the 559 first-party PHP files for the policy guidelines Plugin Check cannot see: bundled plugins, remote code installation, trialware, telemetry, and the authorization model.

Verified clean, so nobody re-checks them: **no trialware or licensing gate** (guideline 5), **no SaaS wrapper** (guideline 6), **no telemetry or user tracking** (guideline 7 — `app/Menu/Analytics.php` is an internal admin menu page, and all 17 `themeum.com` references are docblock `@author`/`@link`), **no direct `$wpdb` queries**, **no update-routine tampering**, and **no trademark problem in the slug**.

## Decision 1: severity tiers, not guideline numbers

Findings are ordered by what happens if they ship, in three tiers:

- **Blocker** — the submission is rejected without a code review.
- **Security** — the reviewer's security email; the plugin is held until fixed.
- **Hygiene** — Plugin Check warnings and directory conventions; fix before submitting, but nothing here holds a review on its own.

Ordering by guideline number would interleave a five-minute fix with a multi-day one. `tasks.md` follows the tiers.

## Decision 2: repeated issues are one task with a regenerating command

An issue occurring across many files is one task carrying its count, two or three representative sites, and the exact command that regenerates the full list. The command is the completion test: the task is done when it returns nothing. This keeps the plan short without making it depend on a location list that goes stale the moment code moves.

## Decision 3: `libraries/framework` is evidence, never a fix target

`CLAUDE.md` records that `libraries/framework` is php-scoper output regenerated by `composer scope`; a hand-edit there is destroyed on the next build. It is read to explain in-scope findings and never patched. The 206 Plugin Check findings rooted there are excluded from every count in `tasks.md`.

This matters most for the authorization finding: the weak check lives in `libraries/framework/Middlewares/AuthMiddleware.php`, but the fix belongs at the route and policy layer in `app/` — which is also the architecturally correct place for it, independent of the constraint.

## Decision 4: `@todo` trajectories are called out, but separately

Findings are anchored to committed code. The one exception is the addon installer, where the *plan* is the violation rather than the current state: today's URL is a local mock route, and the `//@todo: implement cloud url` is what guideline 8 prohibits. Task group 4 removes the mock; the design note here is what stops it being rebuilt.

**Guideline 8 makes the current gateway roadmap unshippable.** The free directory will not accept a plugin that fetches and executes code from themeum.com or kirki.com. The resolution the code already anticipates is publishing each gateway as its own directory plugin — the six entry files carry `Requires Plugins: kirki-ecommerce`, which only resolves against directory slugs, and WordPress will then install and update them through its own machinery with no installer code in this plugin at all. Choosing a different path is a product decision that needs to be made before task group 4 is executed, not after.

## Decision 5: verification is PHP-appropriate, deviating from `config.yaml`

`openspec/config.yaml` requires every task group to end with `npm run typecheck && npm test` from `resources/app/`. Every prior change was frontend; this one is almost entirely PHP, and that command proves nothing about escaping, capability checks, or package contents. Task groups here end with the applicable one of:

- the group's own regenerating `grep` returning nothing,
- `./wpcli plugin check kirki-ecommerce-dist --checks=<slug>` reporting the expected drop,
- `composer install && bin/phpunit` for behavior changes,
- `npm run typecheck && npm test` for the groups that do touch the frontend build.

**The working tree cannot run PHPUnit as it stands.** The last `make:package` run executed `composer install --no-dev` and then `rm -rf vendor/themeum`, so `vendor/phpunit`, php-scoper, and the WP stubs are gone. Task 0.1 restores them. The audit itself was read-only and mutated nothing.

## Decision 6: which findings become spec deltas

Two capabilities carry durable behavior contracts and get deltas; everything else is a task with no delta, because it changes no specified behavior.

- **`plugin-packaging` (MODIFIED + ADDED).** The existing "Package excludes development-only files" requirement names `resources/app/` and `resources/site/` as excluded — exactly what guideline 4 requires shipping. That requirement is modified rather than extended, because it is currently wrong. Added requirements cover the directory-submission constraints the spec never had: no nested plugin headers, no hidden files, and the mandatory `readme.txt`/`LICENSE`.
- **`admin-api-authorization` (new capability).** "An admin endpoint requires a capability, not merely a session" is an invariant worth pinning: once specified, a future route that gates on `is_user_logged_in()` alone is a spec violation rather than an oversight. The new spec describes the target state, so `openspec/specs/` will briefly describe behavior the code does not yet have — normal for a change, but worth knowing while task group 5 is open.

`readme.txt`, escaping, dev-file removal, and the rest specify nothing new and stay in `tasks.md` only.
