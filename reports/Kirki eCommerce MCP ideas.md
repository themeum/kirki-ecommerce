# Grow one sales tool into a store assistant

**Kirki eCommerce can give merchants 43 MCP tools, 7 resources and 10 prompts. Most of the first 25 tools are read-only and wrap code that exists today.** The current StoreServer has one tool, `kirki-ecommerce-sales-report`. That tool uses only 2 of the 16 metric keys in `AnalyticsQueryService`. The other 14 metrics, the Home overview, and the list and show services for orders, products, variants, customers and coupons are ready to wrap. Merchants ask an admin assistant mostly about store data, orders, product text, stock, discounts and customer segments, in that order of evidence. Phase 1 therefore gives read tools for all six areas. Phase 2 adds 13 writes that the code already guards well: fulfillment actions, order notes, coupon create and activate, draft products and stock changes. Phase 3 holds 5 risky writes, such as cancel order and bulk price change. Refunds, hard deletes, `delete-all` bulk actions and the unfinished invoice and payment-link actions must stay out. Resources give fixed, store-wide context, because the framework Resource has a fixed URI and no URI templates. Prompts package merchant routines, such as a morning brief and a monthly close. This set also fills the gaps in WooCommerce MCP, which has no tools for coupons, customers, inventory or analytics, and no resources or prompts. The main limits are outside the tool list: claude.ai and ChatGPT web cannot connect without OAuth, and every admin route uses the same `manage_options` check today.

## The current server uses 2 of 16 analytics metrics

StoreServer is a custom server on the WordPress MCP Adapter. It has its own endpoint, `/wp-json/kirki/ecommerce/v1/mcp/kirki-ecommerce`, a rate limit of 60 requests per minute for each user, and one tool (code: `app/Mcp/Servers/StoreServer.php`, `docs/mcp.md`). The tool checks `manage_options` and calls `get_metric('kpis')` and `get_metric('total_sales_breakdown')` only. It does not return `returning_customer_rate`, although `kpis` gives that value (code: `app/Mcp/Tools/SalesReportTool.php`). `AnalyticsQueryService` has 16 metric keys and a regions drill-down. **Fourteen metrics, `get_regions()` and the Home dashboard overview have no MCP tool** (code: `app/Services/AnalyticsQueryService.php` lines 50–67, `app/Services/DashboardService.php`).

The bundled `framework-mcp` package sets three limits on the design. A Tool has `read_only`, `destructive`, `idempotent` and `open_world` hints, an input schema and an output schema. A Resource must have one static URI; registration fails without it, and the package has no URI templates. A Prompt has simple named arguments with a description and a required flag (code: `vendor/libraries/framework-mcp/src/Tool.php`, `Resource.php`, `Prompt.php`, `Argument.php`). The Server has `before_call` and `after_call` hooks, which can hold an audit log (code: `vendor/libraries/framework-mcp/src/Server.php` lines 309, 324).

Client support decides where each feature goes. **Every major client supports tools. Resources and prompts work in Claude, Claude Code, VS Code and Cursor, but the ChatGPT documentation covers tools only** ([Claude docs](https://claude.com/docs/connectors/building); [VS Code docs](https://code.visualstudio.com/docs/copilot/chat/mcp-servers); [Cursor docs](https://cursor.com/docs/context/mcp); [OpenAI docs](https://developers.openai.com/api/docs/mcp/)). Thus each fact in a resource must also be available from a tool. Claude runs read-only tools without a prompt and always asks before a destructive tool ([Claude review criteria](https://claude.com/docs/connectors/building/review-criteria.md)). Thus the annotations decide what the merchant must confirm.

### How to read the tool tables

Each tool table has the same columns. "Source" tells whether the tool wraps existing code (**Wrap**), wraps existing code with a small change (**Wrap+**), or needs a new query or service (**New**). "Guard" gives three items. The first item is the capability. Today every admin route uses `manage_options` only (code: `routes/api.php`). This report proposes three new tiers: **R** (read reports, catalog, coupons and masked lists), **P** (read full customer personal data), and **W** (safe writes). **A** means `manage_options` plus a server-side approval step. Until the tiers exist, all tools use `manage_options`. The second item is the annotation set: RO (read only), D (destructive), I (idempotent), OW (open world, for example it sends an email). The third item is the confirmation: "none", "2-step" (the tool returns a preview and a short-lived token; a second call with the token does the change), or "2-step+UI" (2-step plus `_meta["anthropic/requiresUserInteraction"]`, which forces a prompt on each call in Claude Code ([Claude Code docs](https://code.claude.com/docs/en/mcp))). Phase 1 is read-only. Phase 2 is safe writes. Phase 3 is risky writes or later.

## Tools by area: 25 reads first, then 13 safe writes, then 5 risky writes

### Analytics and reports: seven tools wrap one existing service

Data questions are the first merchant use case in every source. A vendor guide estimates that 2–3 minutes of report clicks become a 5-second question ([Fudge](https://www.fudge.ai/guides/shopify-sidekick-use-cases/)). Shopify management names analytics and customer segments as main Sidekick topics ([Q3 2025 earnings call](https://www.aol.com/finance/shopify-shop-q3-2025-earnings-001638969.html)). All tools below use the same range arguments as the current tool: presets `today` to `year_to_date` or `custom`, comparison `previous_period`, `previous_year`, `custom` or `none` (code: `app/Services/AnalyticsRangeResolver.php`).

Two notes apply. First, the Home overview counts net sales in a different way from Analytics (code: `docs/analytics.md` section 7). The tool description must say which number it gives, so that the assistant does not mix them. Second, a refund report cannot give refunds by product: a refund row has no link to order items (code: `database/migrations/CreateRefundsTable.php`). Analytics has no traffic, session or conversion data and no export (code: `docs/analytics.md` section 8). Thus questions such as "revenue by traffic source" have no answer today.

A single tool with a `metric` enum is an alternative to the seven grouped tools. Anthropic advises "more tools don't always lead to better outcomes" ([Anthropic Engineering](https://www.anthropic.com/engineering/writing-tools-for-agents)). This report prefers grouped tools: each group has a clear description and a small, specific output schema.

### Orders: the state matrix makes fulfillment writes safe

Order lookup is one of the seven WooCommerce MCP abilities, and "where is my order" is the largest support ticket type, at about 18% of requests per Gorgias data ([InstaWP](https://instawp.com/?p=157729); [eesel](https://www.eesel.ai/blog/gorgias-ai-order-tracking)). Order actions run in a transaction with a row lock, and the state matrix allows only the actions listed for the current status (code: `app/Actions/Order/PerformOrderAction.php` lines 56–160, `resources/data/order-state-matrix.json`). **This existing guard makes fulfillment writes a good phase 2 item.** Each status change fires an event that sends a customer email (code: `app/Events/`, `docs/emails.md` section 2). Thus these tools are open-world and must ask for confirmation.

### Products and inventory: stock lives on the variant, not the product

Stock fields (`available_quantity`, `low_stock_threshold`, `track_inventory`, `allow_back_order`) are on `variants`, and `AvailabilityService::resolve_product_status` rolls them up to a product status (code: `database/migrations/CreateVariantsTable.php`, `app/Services/AvailabilityService.php`). Inventory tools must therefore work at variant level. Restock lists, days-of-cover estimates and low-stock alerts are common assistant jobs ([Let's Talk Shop](https://www.letstalkshop.com/blog/how-to-use-shopify-sidekick-for-inventory-management); [Fudge](https://www.fudge.ai/guides/shopify-sidekick-use-cases/)). Product text is the most common small-business AI use ([Thryv](https://www.thryv.com/guides-resources/ai-and-small-business-adoption-report-2025)). Vendor case studies report a drop from about 15 minutes to under 2 minutes for each description, with a human review ([Sunzinet](https://www.sunzinet.com/en/references/scale-10000-products-ai-content-generation)).

### Coupons and discounts: the clearest lead over WooCommerce

Discounts are the second Sidekick use case, and one prompt replaces 4–5 admin screens ([Fudge](https://www.fudge.ai/guides/shopify-sidekick-use-cases/)). WooCommerce MCP has no coupon abilities ([WooCommerce MCP docs](https://developer.woocommerce.com/docs/features/mcp/)). Kirki coupons are rich: code or automatic, amount-off, free shipping or buy-X-get-Y, product and category targets, customer include and exclude lists, first-time-buyer flag, usage limits and combinations (code: `database/migrations/CreateCouponsTable.php`). Coupon usage counters are atomic (code: `app/Services/CouponService.php`, `claim_usage`). A coupon can be deactivated at once, so create and activate are reversible.

Twenty-five tools in phase 1 is a large first step. ## Seven resources give fixed, store-wide context

The MCP spec calls resources "application-driven": the host decides how to add them to the context ([MCP spec: Resources](https://modelcontextprotocol.io/specification/2026-07-28/server/resources)). In Claude Code, the merchant attaches a resource with an `@` mention ([Claude Code docs](https://code.claude.com/docs/en/mcp)). The framework Resource has only a fixed URI (code: `vendor/libraries/framework-mcp/src/Resource.php`). Thus a resource cannot be "order 1042"; per-entity data must come from tools. The resources below hold store-wide context that changes slowly. Use `audience: assistant` and a high `priority` for the profile and the definitions. Each resource must also be reachable through `get-store-settings` or another tool, for clients without resource support.

| Resource URI | Contents | Source in code | Merchant benefit |
|---|---|---|---|

| `kirki://store/order-lifecycle` | Order, fulfillment and payment statuses; the allowed actions for each status; which action sends which email, and if that email is on. | `resources/data/order-state-matrix.json`, `app/Constants/Order/OrderAction.php`, `docs/emails.md` section 2, `email.json` | The assistant does not propose an action that the store refuses. It warns before an action emails a customer. |
| `kirki://store/analytics-definitions` | Counting rules (sales by `paid_at`, orders by `created_at`, returns by completed refunds), range presets, granularity, top-N limits, Home versus Analytics net sales. | `docs/analytics.md` sections 3 and 7, `AnalyticsRangeResolver.php` | The assistant explains numbers in the same way as the Analytics page. It does not compare two different "net sales" values. |
| `kirki://store/checkout-and-payments` | Enabled payment methods (names only), guest checkout, coupon field, customer note, legal consents. No credentials. | `checkout.json`, `payment.json` (redacted), `OfflinePaymentService`, `legal.json` | Answers checkout questions from customers and staff. |
| `kirki://store/tax-and-shipping` | Tax-inclusive prices, shipping tax, tax regions, shipping zones and methods, a plain summary of the shipping rules. | `tax.json`, `shipping.json`, `config/decisions.php` | Answers "what does shipping to Spain cost?" and checks a quote. |
| `kirki://store/currencies` | Active currencies, base currency, exchange rates, last and next sync time. | `currencies` table, `currency.json` | Explains price differences in other currencies. Shows a stale rate. |
| `kirki://catalog/structure` | Category tree, brands, collections, tags and attributes, with product counts. Capped in size. | Category, brand, collection, tag and attribute services | Gives the assistant the catalog vocabulary for searches and new drafts. |

Claude does not support resource subscriptions ([Claude docs](https://claude.com/docs/connectors/building)). Thus a resource gives a snapshot. Set `last_modified` so that the client can see its age.

## Ten prompts package merchant routines

Prompts are "user-controlled". Clients show them as slash commands, for example `/kirki-ecommerce:morning-brief` in Claude Code ([MCP spec: Prompts](https://modelcontextprotocol.io/specification/2026-07-28/server/prompts); [Claude Code docs](https://code.claude.com/docs/en/mcp)). The client adds the server name, so the prompt names below are short. **Prompts fix the main adoption barrier: 29% of Shopify merchants who do not use AI do not know what the tools can do** ([Shopify AI statistics](https://www.shopify.com/blog/ai-statistics)). Sidekick Pulse shows that proactive daily insight and low-stock alerts are the routines that platforms build first ([Shopify Help Center](https://help.shopify.com/en/manual/ai-powered-tools/sidekick)). All framework arguments are simple strings (code: `vendor/libraries/framework-mcp/src/Argument.php`). Each prompt tells the assistant to show its results before any write and to write only after the merchant agrees.

| Prompt | Arguments | Tools it calls | What the merchant gets |

## Leave money, deletes and stubs out of the first releases

Five groups of operations must not become MCP tools in phases 1 to 3.

**Refunds.** Refund creation calls the gateway `refund()` method when the order has a gateway transaction, so it moves real money (code: `app/Actions/Order/CreateRefundAction.php` lines 74–121, `app/Payment/Providers/PayPal.php` line 248). The refund actions (initiate, approve, decline, mark complete) are commented out until "a dedicated refund state machine" exists (code: `app/Actions/Order/PerformOrderAction.php` lines 109–124). Several refund decisions are still open, such as stock release on a full refund (code: `CreateRefundAction.php` lines 106–108). **Also, the Claude directory does not accept connectors that "transfer money, cryptocurrency, or other financial assets"** ([Claude review criteria](https://claude.com/docs/connectors/building/review-criteria.md)). A later refund tool must copy Stripe's pattern: the tool returns a link, the person approves in the dashboard, and the approval expires after 24 hours ([Stripe MCP docs](https://docs.stripe.com/mcp)). For Kirki, the approval page would be in wp-admin.

**The `send_invoice_email` and `send_payment_link` stubs.** Both return `false` with a `@todo` (code: `app/Managers/OrderManager.php` lines 680–720). A tool on top of them reports a failure every time, or worse, a success that did not occur.

**Hard deletes and bulk "all" actions.** `delete_order()` is a hard delete with no status check, and refunds cascade with the order. `delete_all` deletes every order that matches the list filters (code: `app/Services/OrderService.php` lines 453–507). A single product delete is a hard delete with no trash check (code: `app/Services/ProductService.php` lines 273–313). Customer delete, bulk delete and `delete_all` are plain deletes (code: `app/Services/CustomerService.php` lines 331–400). One wrong filter from an assistant can remove the full order history. Product trash through `change-product-status` gives the safe, reversible path.

**Whole-group settings, base currency and payment providers.** `PUT /settings` replaces a full group. `CurrencyService::set_base` and the payment provider install and config routes have only `manage_options` and validation (code: `app/Services/CurrencyService.php`, `app/Http/Controllers/Api/SettingsController.php`). These changes affect every price and every payment, and they can expose credentials.

**Other items.** Order edit (`PUT /orders/{id}`) rebuilds tax and coupon rows from today's settings, and the edit rule for cancelled orders is an open question (code: `app/Actions/Order/UpdateOrderAction.php` line 121). Customer creation with `create_wordpress_user` creates WordPress accounts. Sample data import (`POST /onboarding/sample-data`) puts test data into a live store. A bulk customer export sends personal data of all customers to the AI provider. A generic "call any REST route" tool hides the annotations and mixes reads and writes; the Claude directory rejects that type of catch-all tool ([Claude review criteria](https://claude.com/docs/connectors/building/review-criteria.md)). Reviews, subscriptions, digital downloads, customer groups and abandoned carts have no backend, so no tool can serve them yet (code: `app/Models/`, `app/Services/CartService.php`).

## Guards must live on the server, not in annotations

**Annotations are hints, not controls.** The spec says that clients "MUST consider tool annotations to be untrusted unless they come from trusted servers", and ChatGPT warns that a write can occur even when a tool says read-only ([MCP spec: Tools](https://modelcontextprotocol.io/specification/2026-07-28/server/tools); [OpenAI docs](https://developers.openai.com/api/docs/mcp/)). Set them on every tool all the same. The Abilities API default for `destructive` is `true` ([Abilities API php-api.md](https://github.com/WordPress/abilities-api/blob/trunk/docs/php-api.md)). If a read tool does not set `read_only`, every client shows it as destructive and asks the merchant each time. Set `open_world` on each tool that sends an email.

**Capabilities and read-only mode.** Every admin route uses `manage_options` now (code: `routes/api.php`). Add the R, P and W capability tiers and a "Store assistant" role. Then the merchant can give an Application Password to a user that cannot change settings. Application Passwords carry all permissions of the user and cannot be narrowed ([InstaWP](https://instawp.com/?p=157729)). Add a global "MCP read-only" setting, on by default. In read-only mode, StoreServer does not list write tools. The spec allows a tools list that varies by authorization ([MCP spec: Tools](https://modelcontextprotocol.io/specification/2026-07-28/server/tools)).

**Confirmation without elicitation.** The MCP Adapter supports elicitation through MRTR only for direct tools, and it rejects continuation fields on ability-backed tools ([mcp-adapter mrtr.md](https://github.com/WordPress/mcp-adapter/blob/trunk/docs/guides/mrtr.md)). The framework registers tools through an ability registrar (code: `vendor/libraries/framework-mcp/src/Registrar/AbilityRegistrar.php`), so Kirki tools probably cannot use elicitation; this is an inference to verify. Also, "an `accept` answer is not independently verified human approval" ([mcp-adapter mrtr.md](https://github.com/WordPress/mcp-adapter/blob/trunk/docs/guides/mrtr.md)). Use the 2-step pattern on the server: the first call returns the planned change and a random, short-lived token bound to the user ID; the second call with the token does the change. Every write returns the stored value after the write.

**Audit log.** The store has no audit trail outside order activities and refund `created_by` fields (code: `database/migrations/CreateOrderActivitiesTable.php`). Use `before_call` and `after_call` on StoreServer to record the user, the tool, the arguments with personal data removed, the result and the time. Take the user from the verified credential, not from the client name. For order actions, also write an order activity that says the change came from the AI assistant, so the merchant sees it on the order timeline.

**Personal data.** List tools mask names and emails. Only `get-order` and `get-customer` give full data, and they need the P tier. Never put personal data in URLs, headers or logs ([MCP spec: Tools](https://modelcontextprotocol.io/specification/2026-07-28/server/tools)). WooCommerce tells merchants that personal data in MCP output is their compliance task ([WooCommerce MCP docs](https://developer.woocommerce.com/docs/features/mcp/)). Kirki's `docs/mcp.md` must say the same.

**Prompt injection from store text.** Order notes, customer notes, cancellation reasons, addresses, coupon titles and imported product text come from people outside the merchant. An assistant with private data, untrusted text and an outbound channel has the "lethal trifecta" ([Simon Willison](https://simonwillison.net/2025/Jun/16/the-lethal-trifecta/)). Return such text in clearly named fields, cap its length and remove markup. No write may start from that text without a fresh confirmation. `add-order-note` with `notify_customer` and `resend-order-email` are outbound channels, so they always need the 2-step confirmation. Tool descriptions must not tell Claude how to behave ([Claude review criteria](https://claude.com/docs/connectors/building/review-criteria.md)).

**Size and errors.** Use `limit` (default 20, maximum 100) and a cursor on every list. claude.ai accepts about 150,000 characters for each result, and Claude Code warns above 10,000 tokens ([Claude docs](https://claude.com/docs/connectors/building); [Claude Code docs](https://code.claude.com/docs/en/mcp)). Return validation failures as tool errors that tell the model what to fix. The current tool already does this (code: `app/Mcp/Tools/SalesReportTool.php`). Keep the 60-per-minute limit and add a lower limit for writes.

**The OAuth gap.** "The web versions of Claude and ChatGPT add connectors through an OAuth sign-in, and they have no field for an Application Password." WordPress and the MCP Adapter have no OAuth server ([mcp-adapter site-owners.md](https://github.com/WordPress/mcp-adapter/blob/trunk/docs/getting-started/site-owners.md)). Today only Claude Code, Claude Desktop through a proxy, and IDE clients can connect. Most merchants use the web apps. An OAuth 2.1 server with CIMD and audience-bound tokens is thus a precondition for wide merchant use, and it is a larger project than any single tool.

## Kirki fills the gaps that WooCommerce MCP leaves open

WooCommerce's canonical abilities cover products (query, create, update, delete), orders (query, status update, add note) and order notes query ([WooCommerce 10.9 post](https://developer.woocommerce.com/2026/05/12/mcp-abilities-api-10-9/); [WooCommerce MCP docs](https://developer.woocommerce.com/docs/features/mcp/)). **It has no abilities for customers, coupons, refunds, inventory or analytics, and it uses no MCP resources or prompts** ([WooCommerce MCP docs](https://developer.woocommerce.com/docs/features/mcp/)). WooCommerce serves its abilities through the adapter's default server, which shows the client only three meta-tools: discover, get info and execute ([WooCommerce MCP docs](https://developer.woocommerce.com/docs/features/mcp/)). One execute tool for reads and writes hides the per-ability annotations from the client's permission prompts.

| Area | WooCommerce MCP | Kirki proposal |
|---|---|---|
| Analytics | None | 8 report tools over 16 metrics, regions and Home overview |
| Coupons | None | Find, get, create, activate or deactivate, update |
| Customers | None | Find, get, segments (lapsed, VIP), tags |
| Inventory | Stock only as a product field | Variant-level stock list, days of cover, relative stock change |
| Orders | Query, status update, note | Plus timeline, total preview, tracking, offline payment, resend email, guarded by the state matrix |
| Product delete | Trash by default, hard delete with `force` | No delete; trash through status change only |
| Resources and prompts | None | 7 resources, 10 prompts |
| Tool surface | 3 meta-tools on the default server | Named tools on StoreServer, with visible annotations |

WooCommerce gets two things right that Kirki should copy: it rejects a status change that does nothing, and it rejects unknown fields before it runs an ability ([WooCommerce 10.9 post](https://developer.woocommerce.com/2026/05/12/mcp-abilities-api-10-9/)). The comparison has limits. WooCommerce has a much larger installed base, and the notes did not confirm whether WooCommerce 11.x added coupon or customer abilities after 10.9.

## Conclusion

The cheapest high-value step is not new code but new wrappers. Twenty of the 25 phase 1 tools reuse services that the admin app already calls, so the risk of phase 1 is low and its value is the highest: data questions and order lookup lead every source on merchant demand. The real design work is in three places that no tool table shows: a capability model finer than `manage_options`, a server-side 2-step confirmation (because ability-backed tools probably cannot use elicitation), and OAuth for the web clients most merchants use.

Kirki's position against WooCommerce is strongest where the WooCommerce MCP is empty: coupons, customer segments, variant-level inventory, analytics, and ready-made routines as prompts. Prompts deserve more weight than their small code cost suggests, because the main barrier for small merchants is not knowing what to ask. Refunds stay last for two reasons, not one: the refund state machine is unfinished, and a money-moving tool closes the Claude directory to the whole connector.
